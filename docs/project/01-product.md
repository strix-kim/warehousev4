# 01-product — ARGO Warehouse

Что это за продукт, для кого, что в нём есть и **чего в нём принципиально нет**.
Границы продукта — главное содержимое этой страницы; механику ищи в 02, схему — в 03,
устройство кода — в 04.

## 1. Питч

Внутренняя веб-система учёта AV-оборудования ARGO Media: каталог техники, сборка
комплекта под мероприятие, выгрузка готового Excel для выезда. Пользователи — только
сотрудники компании, вход по e-mail и паролю через Supabase Auth. Публичной
регистрации, восстановления пароля и гостевого режима нет и не планируется.

## 2. Кто пользователь

**Ролей в интерфейсе нет.** Все вошедшие видят один и тот же экран; таблица
`public.users` клиентом не читается ни разу.

**В базе роли есть** (`admin`, `manager`, `technician`), и разграничение делает RLS.
Разница ролей проявляется как **отказ операции, а не как скрытая кнопка** — это
осознанное следствие того, что прочитать роль на клиенте физически нельзя:
`revoke all on public.users from authenticated`.

> **Ловушка, которую надо знать до того, как «чинить».** Отзыв прав не ломает вход
> только потому, что `private.is_app_member()` и `private.has_any_role()` объявлены
> `security definer`. Вернуть `grant`, «чтобы клиент видел роли», — значит открыть
> таблицу пользователей и не получить взамен ничего. Разбор — `03-data-model` §3.

Язык интерфейса — `ru` по умолчанию, `uz` переключателем, выбор в
`localStorage['argo:language']`. Строки не в словаре, а парой прямо в месте вызова:
`tr(ru, uz)` (`lib/i18n.tsx`). Названия категорий и подкатегорий — отдельным
словарём (`lib/equipmentTaxonomy.ts`).

## 3. Основной сценарий

| Шаг | Маршрут / действие |
|---|---|
| 1 | `/login` — вход по паролю |
| 2 | `/` — главная, выбор «Оборудование» или «Списки» |
| 3 | `/lists/new` — редактор: поиск моделей, количество, явный выбор серийных единиц |
| 4 | Сборка позиций: серийные (`equipment_id` + S/N) → количественные → остаток как `planned` |
| 5 | Формат выбирается кнопкой в момент скачивания — «Рабочий Excel» или «С реквизитами». Второй требует названия, заказчика и площадки; первый — ничего |
| 6 | Сохранить в системе — **необязательно** |
| 7 | Скачать `.xlsx` — работает и без сохранения |
| 8 | Выезд |

**Ключевое решение продукта: шаги 6 и 7 независимы.** Интерфейс говорит это прямо
(«Excel скачан. Сохранять список в системе необязательно»), и при неудачном сохранении
тоже («Файл всё ещё можно скачать»). **Excel — это продукт, база — опциональный архив.**
Всё остальное устройство редактора подчинено этому: сохранение не является гейтом ни
для чего.

Режим списка (`specific` / `abstract`) пользователь не выбирает — он выводится
автоматически: `specific`, если ни одна позиция не осталась `planned`.

Excel собирается целиком в браузере, самописный OOXML + ZIP без библиотеки
(`features/lists/xlsxExport.ts`). Реквизиты ООО «ARGO-MEDIA» зашиты в код.

## 4. Что входит в продукт

Шесть страниц на семи маршрутах, все ленивые, каждая под своей границей ошибок:

| Маршрут | Страница | Что делает |
|---|---|---|
| `/login` | `LoginPage` | Вход, переключатель RU/UZ |
| `/` | `HomePage` | Две живые плитки + «Сотрудники» со статусом «Скоро» |
| `/equipment` | `EquipmentPage` | Каталог: поиск, фильтры категории/подкатегории/статуса, пагинация, drawer-карточка, редактирование модели и единицы |
| `/equipment/new` | `EquipmentCreatePage` | Заведение позиции: «серийная» / «по количеству» |
| `/lists` | `ListsPage` | Реестр сохранённых документов, drawer с составом, повторный экспорт, удаление |
| `/lists/new`, `/lists/:listId/edit` | `ListEditorPage` | Сборка комплекта, сохранение, выгрузка Excel |

**Клиент обращается ровно к трём таблицам и четырём RPC:**

| Таблицы | RPC |
|---|---|
| `equipment`, `equipment_lists`, `equipment_movements` | `create_equipment_list_document`, `update_equipment_list_document`, `update_equipment_model_and_unit`, `count_equipment_model_units` |

Сквозные механики: двуязычие через `tr`; постоянный кэш в `localStorage`
(`lib/persistentCache.ts`); прогрев чанков и первичных данных после входа; drawer'ы
с Escape и стартовым фокусом; локальные WebP-фотографии по ключу `бренд::модель`.
Подробности — `02-decisions`.

## 5. Границы продукта — чего в нём НЕТ

**Жизненного цикла списков не существует** (решение прораба, с10). Подтверждения,
выдачи, возврата, истории статусов и расчёта дефицита в продукте нет и не планируется.
Продукт — это собрать список, сохранить, скачать документ. Удалены и код, и схема:
таблицы `reservation_status_history` и `equipment_reservation_items`, RPC
`transition_equipment_list_status` и `reservation_shortages`, колонки
`reservation_status`, `confirmed_at`, `issued_at`, `returned_at`, `status_changed_at`,
`status_changed_by`, `shortage_snapshot`, триггеры `trg_reservation_status_history` и
`trg_guard_reservation_list_update`, признак `advanced_features`.

> **`reservation_start` / `reservation_end` ЖИВЫ** — это **дата мероприятия**,
> реквизит документа. Имя осталось от удалённой подсистемы. На этих колонках стоят
> карточка реестра и фильтр периода; «за компанию» не чистить.

**Предыдущего продукта на Vue в дереве нет.** 173 файла и 37 636 строк удалены в с4;
`src/` — это ровно `src/react`. Код не потерян и достаётся из git-истории
(`git show 4dd010c:src/pages/<файл>.vue`) — как образец бизнес-логики смотреть можно,
возвращать в дерево нельзя. Оттуда же ушли события, точки монтажа, отчёты, дашборд,
управление пользователями и демо дизайн-системы.

Нет по факту кода: раздела «Сотрудники» (плитка помечена «Скоро» и не является
ссылкой); регистрации, восстановления пароля, приглашений, профиля, MFA; управления
ролями из интерфейса; загрузки собственных фотографий; печати, PDF, отправки по почте,
интеграций; автотестов и CI; сборщика ошибок (есть только шов `setErrorSink` под него).

## 6. Масштаб данных

**Прод на 2026-08-22** (сверено выборкой): `equipment` — **1 481 строка / 1 877 штук**,
218 моделей, 7 категорий и 56 подкатегорий, локация одна («Офис»);
`equipment_movements` — 1 391 (все `status_normalized`, след импорта);
`equipment_lists` — 6; `users` — **1, аккаунт ровно один**; `events` — 4,
`mount_points` — 9 (обе таблицы клиентом не используются).

Справочник картинок: 176 моделей с фотографией (`public/equipment-images/*.webp` и
`generated/equipmentImages.ts` — 176 записей, числа сходятся), остальные показывают
иконку категории.

Пределы, зашитые в код: страница каталога — 50 записей, на узком экране 8; реестр
документов — последние 50, дальше из интерфейса не добраться; история движения
единицы — 50 записей. Полная выгрузка каталога для редактора идёт пачками по 1000 —
разбор ограничения Data API и его последствий — `02-decisions` §5.

## 7. Где продукт живёт

| Что | Значение |
|---|---|
| Репозиторий | `github.com/strix-kim/warehousev4`, публичный; `main` = прод |
| Хостинг | Vercel, проект `warehousev4`; SPA-рерайт всего на `/`, кэш- и security-заголовки в `vercel.json` |
| Бэкенд | Supabase `warehousev4` (`umbqiktyqlfqqgupxqdm`) — Postgres + Auth + Data API, обращение из браузера напрямую |
| Runtime сборки | Node 22.x; сборка `tsc -b && vite build` |
| Переменные окружения | `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` — **обе попадают в бандл и читаются любым посетителем** |
| Локально | `npm run dev` → `http://localhost:5180/` (strictPort); без `.env` сборка валится гейтом |

Схема, данные, политики и настройки Auth живут вне git — источник правды раздвоен,
и единственный мост между половинами — миграции в `supabase/migrations/`. Обратно из
прода в файлы ничего само не едет.
