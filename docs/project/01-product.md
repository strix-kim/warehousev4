# 01-product — ARGO Warehouse

Отвечает на вопрос «что это за продукт, для кого, что в нём есть и чего в нём НЕТ».
Все якоря `файл:строка` проверены чтением файла при написании страницы.

## 1. Питч

ARGO Warehouse — внутренняя веб-система учёта AV-оборудования компании ARGO Media:
каталог техники, сборка комплекта под мероприятие и выгрузка готового Excel-документа
для выезда. Пользователи — только сотрудники ARGO Media, вход по паролю через Supabase
Auth (`features/auth/AuthProvider.tsx`, `signInWithPassword`); публичной регистрации,
восстановления пароля и гостевого режима в коде нет.

## 2. Кто пользователь

Что установлено кодом, а не README:

| Факт | Где подтверждается |
|---|---|
| Вход только e-mail + пароль, без OAuth, magic link и sign-up | `features/auth/LoginPage.tsx`, `AuthProvider.tsx` |
| Плейсхолдер логина — `name@argomedia.uz`, подпись «Используйте учётную запись ARGO Media» | `LoginPage.tsx` |
| Нет сессии → любой маршрут редиректит на `/login` | `app/App.tsx`, `App.tsx` |
| Аватар в сайдбаре — «Видеоинженер» / `video-engineer-avatar.png` | `App.tsx` |
| Локация в сайдбаре захардкожена: «Офис · Ташкент» | `App.tsx` |
| Два языка интерфейса, ru по умолчанию, uz переключателем; выбор в `localStorage['argo:language']` | `lib/i18n.tsx`, `i18n.tsx` |
| Строки не в словаре, а парой прямо в месте вызова: `tr(ru, uz)` | `i18n.tsx` |
| Смена языка переписывает `<html lang>` и `document.title` | `i18n.tsx` (стартовое значение `lang="ru"` — `index.html:2`) |
| Названия категорий/подкатегорий переводятся отдельным словарём (55 подкатегорий + 7 категорий) | `lib/equipmentTaxonomy.ts` (69 строк) |

**Ролей в интерфейсе нет.** `grep -rn "role" src/react` вне HTML-атрибутов `role="…"`
и `aria-*` даёт 0 совпадений; таблица `public.users` клиентом не читается ни разу
(клиент обращается только к `equipment`, `equipment_lists`, `equipment_movements`,
`reservation_status_history`). Все вошедшие видят один и тот же интерфейс.

При этом в базе роли есть — `admin`, `manager`, `technician`
(`scripts/2026-08-19_reservations_history_rls.sql:897, 911, 991`), и разграничение
делает RLS через `private.has_any_role()`. Разница ролей проявляется как отказ операции,
а не как скрытая кнопка. Причина, по которой «прочитать роль на клиенте» невозможно:
`scripts/2026-08-19_security_performance_hardening.sql:6` —
`revoke all on table public.users from authenticated`.
**Вместе с этим фактом обязателен второй:** `private.is_app_member()` и
`private.has_any_role()` объявлены `security definer`
(`scripts/2026-08-19_reservations_history_rls.sql:9-21`, `:23-28`), поэтому отзыв прав
авторизацию не ломает. Отменить `revoke`, «чтобы клиент видел роли», — значит открыть
таблицу пользователей, не получив ничего взамен.

Как они работают (выводится из UI, не из README): в сайдбаре первым слотом стоит
быстрое действие «Новый список → Собрать комплект» (`App.tsx`, `.sidebar__quick-action`;
декоративный блок «Быстрый процесс 01/02/03» снят в с8), а главная предлагает два входа —
«Оборудование» и «Списки оборудования» — плюс прямую ссылку «＋ Создать список» в редактор
(`features/home/HomePage.tsx`, с8).

## 3. Основной сценарий

По фактическим маршрутам `app/App.tsx`:

| Шаг | Маршрут / действие | Якорь |
|---|---|---|
| 1 | `/login` — вход по паролю | `App.tsx` |
| 2 | `/` — главная, выбор «Оборудование» или «Списки» | `App.tsx`, `HomePage.tsx` |
| 3 | `/lists/new` — редактор списка: поиск моделей, количество, явный выбор серийных единиц | `App.tsx`, `ListEditorPage.tsx` |
| 4 | Сборка позиций: серийные (`equipment_id` + S/N) → количественные → остаток как `planned` | `ListEditorPage.tsx` |
| 5 | Формат выбирается в момент скачивания кнопкой — «Рабочий Excel» или «С реквизитами» (с8; селектора «Формат Excel» больше нет). Второй требует названия, заказчика и площадки; первый — ничего | `ListEditorPage.tsx`, `exportList(documentMode)` |
| 6 | Сохранить в системе (RPC `create_equipment_list_document` / `update_equipment_list_document`) — **необязательно** | `ListEditorPage.tsx`, `features/lists/api.ts`, `api.ts` |
| 7 | Скачать `.xlsx` — работает и без сохранения; имя файла `2026-08-21_Имя_рабочий.xlsx` / `…_на-согласование.xlsx`, пустое имя списка → автоимя по дате и времени (с8) | `ListEditorPage.tsx`, `exportList`; `xlsxExport.ts`, `downloadEquipmentListXlsx` |
| 8 | Выезд |  |

Ключевая деталь продукта: **шаги 6 и 7 независимы.** После экспорта интерфейс прямо
говорит «Excel скачан. Сохранять список в системе необязательно» (`ListEditorPage.tsx`),
а при неудачном сохранении — «Не удалось сохранить список. Файл всё ещё можно скачать»
(`ListEditorPage.tsx`). Excel — это продукт, база — опциональный архив.

Режим списка (`specific` / `abstract`) пользователь не выбирает: он выводится
автоматически — `specific`, если ни одна позиция не осталась `planned`
(`ListEditorPage.tsx`).

Ветка «учёт выдачи» (`/lists`, drawer сохранённого списка): статусы
`draft → confirmed → issued → returned` (`ListsPage.tsx`), переходы через RPC
`transition_equipment_list_status` (`lists/api.ts`), повторная выгрузка Excel из
сохранённого списка (`ListsPage.tsx`), удаление списка (`ListsPage.tsx`).
Эта ветка в тексте UI подана как необязательная: «Состав, доступность и **необязательный**
учёт выдачи» (`ListsPage.tsx`).

Excel формируется целиком в браузере: самописный OOXML + ZIP без библиотеки
(`features/lists/xlsxExport.ts`, 266 строк). Реквизиты ООО «ARGO-MEDIA» зашиты в код
(`xlsxExport.ts`) — адрес, телефон, р/с, ИНН, ОКЭД. Экранирование пользовательского
текста в XML **есть** (`xlsxExport.ts`: `&`, `<`, `>`, `"`, `'`).

Сквозные механики:

- **Постоянный кэш** в `localStorage` (`lib/persistentCache.ts`, префикс `argo-warehouse:v3:`,
  максимум 64 записи). TTL: каталог и списки — 10 мин (`equipment/api.ts`, `:109`;
  `lists/api.ts`, `:126`), справочник категорий — 24 ч (`equipment/api.ts`),
  дефициты и история — 5 мин (`lists/api.ts`, `:248`).
- **Агрессивный прогрев** после входа: три таймера подгружают все чанки и первичные данные
  (`App.tsx`), плюс предзагрузка изображений следующей страницы каталога
  (`EquipmentPage.tsx`).
- **Drawer'ы** с Escape и стартовым фокусом (`lib/useModalLayer.ts`; `EquipmentPage.tsx, 423`,
  `ListsPage.tsx, 451`, `ListEditorPage.tsx, 714`).
- **Фотографии оборудования** — локальные WebP, сопоставление по ключу `бренд::модель`
  (`generated/equipmentImages.ts`, `features/equipment/EquipmentVisual.tsx`).
- **Статусы резервирования** и история движения оборудования (`equipment_movements`,
  `reservation_status_history`).

Клиент обращается ровно к 4 таблицам и 5 RPC:

| Таблицы | RPC |
|---|---|
| `equipment`, `equipment_lists`, `equipment_movements`, `reservation_status_history` | `create_equipment_list_document`, `update_equipment_list_document`, `update_equipment_model_and_unit`, `transition_equipment_list_status`, `reservation_shortages` |

## 5. Что НЕ входит в продукт

Это самый важный раздел страницы. До с4 в репозитории физически лежал **предыдущий
продукт на Vue — 173 файла, 37 636 строк**, в семь раз больше живого кода.
**В с4 он удалён из рабочего дерева целиком**, вместе с четырьмя неиспользуемыми
ассетами в `public/`: репозиторий сократился с 440 файлов до 263, а `src/` теперь
это ровно `src/react` (23 файла, 5 083 строки). Основной бандл при этом не изменился
ни на байт (358.76 КБ / 110.29 gzip) — доказательство, что удалённое и раньше
не участвовало в сборке.

Код Vue-версии не потерян: он жив в git-истории и достаётся оттуда в любой момент —
`git show 4dd010c:src/pages/<файл>.vue`. Смотреть как образец бизнес-логики можно,
возвращать в дерево нельзя.

Пределы, жёстко зашитые в код: страница каталога — 50 записей (`equipment/api.ts`),
на узком экране 8 (`EquipmentPage.tsx`); реестр документов — последние 50
(`lists/api.ts`, `.limit(50)`), дальше 50-го из интерфейса не добраться; история
движения единицы — 50 записей (`equipment/api.ts`).

Ещё два предела **в код не зашиты** — они зависят от настройки `db-max-rows` Data API,
а её значение для этого проекта **не установлено**: `supabase/config.toml` в репозитории
нет, конфигурация нигде не зафиксирована. Устанавливается: Supabase Dashboard →
Settings → API → Max rows либо мостом Supabase MCP. Полный разбор — `04-architecture.md` §8,
здесь коротко:

- **Полная выгрузка каталога** идёт пачками по 1000 (`equipment/api.ts`,
  `batchSize` на `:111`). Условие выхода `if (batch.length < batchSize) break` (`:124`)
  НЕ различает «таблица кончилась» и «сервер обрезал страницу». При `db-max-rows` ровно
  1000 логика верна; при меньшем значении цикл выйдет после первой итерации, и редактор
  списка молча получит усечённый склад. Поэтому утверждение `AUDIT:56` («все 1481 записи
  загружаются пакетами, лимит Data API в 1000 строк каталог не обрезает») **из репозитория
  не проверяется**: оно верно лишь при `db-max-rows >= 1000`.
- **Справочник категорий** запрашивает 2000 строк (`equipment/api.ts`,
  `.range(0, 1999)` на `:154`), но получит не больше `db-max-rows` — то есть по умолчанию
  1000, а не 2000. `.order()` в этом запросе НЕТ ни одного, значит подмножество
  произвольное, а не «первые N». При заявленных 1481 позиции в проде (`AUDIT:53`, `:56`;
  само число репозиторием не подтверждается) справочник типов и подтипов, вероятнее всего,
  неполон **уже сейчас** — а не «станет неполным при росте за 2000». Результат кэшируется
  на 24 часа (`:150`), то есть промах закрепляется на сутки.

| Проект Supabase / URL прода | **не установлено** — `.env` в git не хранится (`.gitignore`), домен проекта в репозитории не встречается | — |
| `node_modules` | Каталога не существует; установка не выполнялась | `ls` |

**Мост агента к проду не подключён.** Supabase MCP и Vercel MCP из этой сессии смотрят
в другую организацию/аккаунт, поэтому ни схема прод-базы, ни её данные, ни состояние
деплоя из кода не проверяемы. Всё, что в этой странице сказано про базу, — это
утверждения о SQL-файлах в репозитории и о TypeScript-типах, а не о живой схеме.

**DDL базовых таблиц (`users`, `equipment`, `equipment_lists`, `events`, `mount_points`,
`reports`) в репозитории отсутствует.** В `supabase/migrations/` лежат 4 файла (все от
19.08.2026, только про редактирование и удаление списков), в `scripts/` — 6 SQL-файлов
поверх уже существующей схемы. Поэтому фраза «у `equipment` есть колонка X» означает
«в типе `features/equipment/types.ts` есть поле X», и не более.

Отдельно: `tracking_mode` и `inventory_code` (`types.ts`) — **не колонки базы**,
а результат разбора строки `serialnumber` на клиенте (`equipment/api.ts`).
Та же эвристика продублирована в SQL-бэкфилле
(`scripts/2026-08-19_reservations_history_rls.sql:247`) — два независимых парсера одной
строки.

Порядок применения `scripts/*.sql` относительно `supabase/migrations/` нигде не
зафиксирован, механизма применения нет (`supabase/config.toml` отсутствует, пакета
`supabase` в `package.json` нет, `.github/` нет). Значит, действует ли `grant` или
`revoke` на `public.users`, из репозитория не определить.

## 8. Расхождения README/AUDIT с кодом

### AUDIT — где расходится с кодом

- **AUDIT:69** называет клиентскую проверку уникальности серийного номера «теоретической
  гонкой». Преуменьшение сразу по двум линиям.
  **Первая:** `UNIQUE` на `equipment.serialnumber` в репозитории отсутствует, значит это
  не гонка, а отсутствие ограничения. `serialNumberExists` (`equipment/api.ts`)
  живёт только в браузере, пары в базе у неё нет — **это дыра**.
  **Вторая:** проверка проваливается не только в гонке, а при ЛЮБОМ сбое запроса.
  `checkSerial` (`EquipmentCreatePage.tsx`) обёрнут в `try/catch`, где `:76-77` —
  `} catch { return false }`, а `serialNumberExists` бросает на любой ошибке
  (`equipment/api.ts`). Сеть, 401, ответ PostgREST с ошибкой — всё трактуется как
  «дубля нет», и `handleSubmit` (`:86`) идёт дальше в `createEquipment` (`:94`). Это шире,
  чем классический check-then-insert: окно не «между проверкой и вставкой», а «проверки
  не было вовсе».
  Про регистр — точная формулировка: и проверка (`.ilike`, `api.ts`), и вставка
  (`input.serialnumber?.trim()`, `api.ts`) работают с обрезанной строкой, но `ilike`
  регистронезависима, поэтому «sn-001» при уже существующем «SN-001» она как раз
  **поймает**. Двумя разными строками эти значения лягут в базу только если проверку
  обойти — конкурентно или через сбой запроса выше; удержать их нечем, ограничения нет.
  Так же это изложено в `03-data-model.md` (разбор расхождений с AUDIT).
- **AUDIT:52** утверждает, что смешанный список получает реальные `equipment_id`. Это
  верно (`ListEditorPage.tsx`), но сервер не сверяет присланный текст
  `brand/model/type/subtype` с реальной строкой оборудования — он вставляет его дословно
  (`supabase/migrations/20260819131611_edit_saved_equipment_lists.sql:101-116`), проверяя
  только существование `equipment_id` (`:53-65`). Расчёт дефицита при этом джойнит склад
  именно по этому денормализованному тексту. **Это дыра в целостности**, аудитом не
  названная.
- **AUDIT:13** («предупреждения о нехватке без запрета сохранить документ») описывает
  фичу, но не называет цену: количество не сверяется с остатком при сохранении вообще
  (`create_equipment_list_with_items` проверяет членство, имя, `list_mode`, парность дат,
  непустоту items и существование `equipment_id` —
  `scripts/2026-08-19_reservations_history_rls.sql:625-653` — и не проверяет
  `requested_count`). Единственный физический гейт — переход `confirmed → issued`
  (`:754-783`). До выдачи в базе может лежать бронь на любое число единиц.
- **AUDIT:17** приводит размер бандла (≈354 КБ / 109 КБ gzip) — **проверить нечем**:
  `node_modules` нет, сборка не запускалась.
- **AUDIT:53, :56, :65** оперируют числами из прод-базы (1481 позиция, 0 списков,
  11 дублей SN) — **из репозитория не проверяются**, мост слеп.
- **AUDIT:34** честно признаёт отсутствие focus trap. Добавление к нему: возврат фокуса
  на триггер реализован в `components/AppSelect.tsx` и
  `components/AppDatePicker.tsx, 159`, но не в трёх drawer'ах — проект не согласован
  сам с собой.

### Что README и AUDIT не упоминают вовсе

- Excel собирается своим кодом без библиотеки, с зашитыми банковскими реквизитами
  ARGO-MEDIA (`xlsxExport.ts`).
- У списков два формата документа — «Рабочий список» и «На согласование + реквизиты»
  (`ListEditorPage.tsx`).
- Расчёт доступности в редакторе — эвристика по подстрокам русского текста статуса
  («не », «диагност», «в н») поверх кэша до 10 минут (`ListEditorPage.tsx`).
- Фолбэк на «legacy»-схему списков срабатывает при ЛЮБОЙ ошибке первого select, включая
  сетевую и 401 (`lists/api.ts`, дубль `:135-150`), и тогда всем спискам
  присваивается `reservation_status: 'draft'` (`:86`) — выданный список показывается как
  черновик, и это кэшируется на 10 минут. Для сравнения, `fetchReservationShortages`
  (`:226`) и `fetchReservationHistory` (`:254`) гейтятся по кодам ошибок.
