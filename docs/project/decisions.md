# Decisions — ARGO Warehouse

Журнал решений: что решили и почему. **Append-only, только-на-запись.**
В обычной работе НЕ читается — «как есть сейчас» отвечают библия 01–06 и
`current-state.md`. Открывается точечно (grep по ключу) при вопросе «почему решили X»
или в `/doc-audit`.

Формат строки: **дата · сессия · решение · почему**.

## Сессия 1 — 2026-08-20

Постановка харнесса. Решения приняты прорабом в ходе сессии; агент исполнял.

**Харнесс копируется в каждый проект, а не выносится в общее место.**
Прораб: «в каждом проекте должны быть свои данные, свой CLAUDE и всё остальное —
чтобы я зашёл в проект, нажал `/session-start`, и мы работали». Плюс: всё
версионируется вместе с репозиторием и переезжает с ним. Минус (дрейф трёх копий)
снят отдельным решением ниже.

**Дрейф между проектами лечится тем, что система ОДНА.** Прораб: «это не должно быть
одной, это одна система — просто внутренний хард каждого проекта свой». Следствие,
зафиксированное в `workflow.md`: ритуалы, имена скиллов, нумерация шагов и шаблон
хэндофа обязаны совпадать между проектами; расходиться имеют право только две
секции — «Гейты стека» и «Мост». Проверка парности внесена в `/doc-audit` отдельным
пунктом «межпроектная сверка».

**Роль прораба в этом проекте перевёрнута относительно соседнего.**
В Roblox-проекте прораб — новичок, и `CLAUDE.md` велит объяснять концепции через его
стек. Здесь React/Supabase — ЕГО стек, и он знает его лучше, чем агент знает продукт.
Поэтому блок «Кто прораб» переписан: не объяснять основы, объяснять только
нестандартное; возражать до исполнения, а не после. Без этой правки харнесс начал бы
растолковывать специалисту его же инструменты.
**УТОЧНЕНО ниже в этой же сессии** («Прораб — фронтенд-специалист, а не эксперт
во всём»): формулировка «знает лучше» верна для фронтенда и неверна для бэкенда,
базы и инфраструктуры.

**Автоматического push после чекпоинта НЕТ.**
Ключевое расхождение с соседним проектом, где push безобиден. Правило: работа в ветке
`session-N-тема`, push ветки свободен (превью-деплой), слияние в `main` — отдельное
действие только по явной команде прораба. Молча выкаченный чекпоинт назван в скиллах
самой дорогой ошибкой проекта.
**УТОЧНЕНО ниже в этой же сессии** («`main` = прод — это ДОПУЩЕНИЕ»): само основание
правила в с1 не проверено, проверка отложена на первую рабочую сессию.

**Схема Supabase объявлена вторым источником правды.**
Прямая аналогия с place-файлом в Roblox-проекте: рядом с репозиторием живёт состояние,
которого git не видит. Отсюда правило «схема — только миграциями», требование
фиксировать миграцией даже то, что применено кликами, и запрет на запись в прод-базу
без разрешения прораба на каждое действие.

**Легаси-Vue: правила сносим, код оставляем.** Решение прораба по прямому вопросу.
Снесены `.cursorrules`, семь файлов `.cursor/rules/*.mdc`, `.eslintrc.json`,
`vitest.config.js`; `docs/ARCHITECTURE.md` переписан под React. Код (173 файла,
37 636 строк) остаётся на диске и объявлен «мёртвой зоной» правилом 7 `CLAUDE.md`.
Почему сносили именно правила: они не просто устарели, а активно врали — предписывали
Vue 3, Pinia, PrimeVue, Tailwind и Bento Grid в проекте, где ничего этого нет. Любой
агент, прочитав их, начал бы писать Vue в React-проекте.

**`.prettierrc` не тронут, в отличие от двух других конфигов.** Он выглядит таким же
«призраком без пакета», но его настройки точно совпадают с фактическим стилем
`src/react` — то есть это действующая конвенция, а не мусор. Разница зафиксирована в
`tooling.md`, чтобы будущий агент не снёс его «заодно».

**Библия сокращена с девяти страниц до шести.** В соседнем проекте 01–09 включают лор,
монетизацию и ретеншен — для внутренней системы учёта этих слоёв не существует.
Взяты: `01-product`, `02-features`, `03-data-model`, `04-architecture`, `05-roadmap`,
`06-design-system`. Живые артефакты (`current-state`, `decisions`, `backlog`,
`handoffs/`) — как в соседнем проекте, один в один.

**Библия пишется по коду, а не по README и AUDIT.** Оба файла уже уличены в
расхождениях с кодом, поэтому агентам-авторам было прямо запрещено брать факты оттуда,
а каждый якорь `файл:строка` предписано проверять чтением. Основание — то же, что
и для сноса `.cursorrules`: доки, которые врут, хуже отсутствующих, потому что агент
им верит.

**Проверка призрачных якорей внесена в `/doc-audit` с первого дня.**
В соседнем проекте она появилась только на сотой сессии, после того как распил модуля
молча оборвал восемь ссылок. Здесь заводим сразу: смысловой дрейф видно глазами,
адресный — не видно, пока не пойдёшь по ссылке. Проверка уже окупилась в этой же
сессии — критик полноты нашёл три призрачных якоря из двенадцати проверенных и целую
зону с систематически смещёнными адресами.

**Аналог двухклиентного прогона — `/rls-verify` под двумя аккаунтами.**
Обоснование то же: один аккаунт маскирует дыры в правах так же, как одиночный запуск
маскирует баги репликации, потому что автор — владелец всех своих записей. Отдельно
записано требование ВТОРОГО ПРОФИЛЯ браузера, а не второй вкладки: сессия Supabase
живёт в `localStorage`, и две вкладки делят один аккаунт.

**Прораб — фронтенд-специалист, а не «эксперт во всём».** Первая формулировка блока
«Кто прораб» называла его экспертом по своему стеку; прораб поправил. Разница
операционная, а не вежливая: фронтенд ему объяснять не надо, а бэкенд, база и
инфраструктура — не его повседневная зона, и там объяснять НУЖНО, только коротко и по
делу, а не курсом с нуля. Формулировка правится в `CLAUDE.md` и `AGENTS.md` парно.

**`main` = прод — это ДОПУЩЕНИЕ, а не установленный факт.** В с1 проверить было нечем:
моста к проекту нет, `.vercel/` в клоне отсутствует, есть только `vercel.json`.
Осторожный режим (ветка, запрет авто-push, слияние по команде) введён всё равно —
потому что цена ошибки несимметрична: лишняя ветка стоит одной команды, случайная
выкатка в прод стоит инцидента. Проверка отложена прорабом на первую рабочую сессию
в репозитории проекта; опровергнется — правило смягчается ЯВНЫМ решением со строкой
здесь же.

**Приоритет вех выведен из цены отказа, а не из бизнес-ценности.** Первой поставлено
восстановление схемы в репозитории: пока DDL базовых таблиц нет в git, вся работа с
данными идёт вслепую. Прорабом порядок не подтверждён — помечено в `05-roadmap` как
предложение агента.

## Сессия 2 — 2026-08-20

Первая рабочая сессия. Цель — зафиксировать прод-схему в git.

**Baseline кладётся в `supabase/migrations/` под версией `00000000000000`, а не
отдельным файлом-снимком вне миграций.** Рассматривались три варианта: `supabase/schema/`
как документ (нулевой риск, но нарушает правило 4 «схема — только миграциями»),
обычная миграция с текущей датой (встала бы ПОСЛЕ `20260819*` и при прогоне на чистой
базе всё сломала), нулевая версия (идёт первой, порядок восстановления правильный).
Выбран третий. Риск повторного применения снят идемпотентностью: весь файл — это
`if not exists` и `drop … if exists`, поэтому на существующей базе он не меняет ничего.
Регистрировать его в `supabase_migrations.schema_migrations` не стали: это запись в
прод, а выгода нулевая, пока в проекте нет Supabase CLI.

**Baseline не переснимается при каждой миграции.** Он описывает стартовую точку,
поверх которой миграции накатываются по порядку, — а не «текущее состояние». Переснимать
имеет смысл только после большой ручной правки в дашборде. Иначе два источника правды
разъедутся молча.

**Расхождения схемы с репозиторием записаны как долги, а не чинятся на месте.**
Найдено пять (`serialnumber not null` против TS, `users.id` без FK на `auth.users`,
удаление списков по почтовому адресу, дубль FK и четыре триггера на `mount_points`,
неиспользуемый GIN-индекс). Ни одно не чинилось: цель сессии — зафиксировать схему,
а не менять её, и правка прод-схемы требует отдельного разрешения прораба на каждое
действие. Особенно это касается `users.id`: добавление FK потребует сверки строк.

**Данные прода вписаны в `current-state` числами.** Не «в базе есть оборудование», а
1481 позиция, 1391 движение, ноль списков, один аккаунт. Последнее число меняет
планирование: `/rls-verify` объявлен неисполнимым до заведения второго аккаунта — иначе
скилл, обязательный для всех задач про права, тихо превращается в ритуал без содержания.

**Проверка полноты выписки сделана машинной, а не глазами.** Из прода выгружен список
имён всех 134 объектов и сверен с файлом через `grep -oFf`. Правило сессии 1
(«отрицательный результат поиска — самое лёгкое место соврать») применено к себе:
утверждение «ничего не пропущено» на 134 объектах вычиткой не доказывается.

**Допущение с1 «`main` — это прод» подтверждено фактом и осталось правилом.**
20 из 20 последних деплоев Vercel — `target: production`, `githubCommitRef: main`.
Осторожный режим не смягчается: он теперь опирается на факт, а не на цену ошибки.

## Сессия 3 — 2026-08-20

**Осторожный режим слияния в `main` снят — прораб.** Основание не техническое, а
продуктовое: ARGO Warehouse — внутренняя система для нескольких сотрудников, а не
публичный сервис. Внешних пользователей нет, аптайм ничего не приносит и не теряет,
откат стоит `git revert` плюс минуты пересборки. Ритуал «слияние только по отдельной
команде» тормозил каждую сессию ради риска такого размера. Прямая цитата прораба:
«не бойся пушить мейн… вообще не страшно».

**Правило разделено надвое: «строг к базе, спокоен к коду».** Агент возразил против
сплошного смягчения и предложил разделение, прораб не оспорил. Причина в асимметрии
отката: прод-код возвращается ревертом за минуту, а удалённые или испорченные строки
в базе не возвращаются ничем. Поэтому **запись в прод-базу (данные, схема, политики)
осталась под разрешением на каждое действие** — правило 8 не смягчалось, оно
переписано так, чтобы два разных риска перестали лежать под одним заголовком.

**Осталось одно условие слияния, и оно про содержимое: сливаем ПРИНЯТОЕ.** Не
«разрешено — значит что угодно»: в `main` едет чекпоинт, подтверждённый прорабом, с
зелёными `npm run check` и `npm run build`. Это не остаток осторожности, а старое
правило «поверх непринятого не строим», просто теперь оно единственное.

**Смена политики = grep по всему харнессу, а не правка `CLAUDE.md`.** Политика жила
текстом в восьми местах; после правки двух файлов правил четыре скилла продолжали бы
диктовать старое будущим сессиям — скиллы читаются агентом как инструкция и переживают
любой чат. Отсюда правило на будущее: меняешь правило — ищи все его копии
(`grep -rn` по `.claude/skills/`, `docs/system/`, `CLAUDE.md`, `AGENTS.md`).

**Проект перенесён на ASCII-путь, а не «обойдён» симлинком или переименованием папки.**
Из трёх вариантов выбран самый радикальный, потому что два других лечат симптом:
симлинк разыменовывается частью инструментов обратно в исходный путь, а переименование
родительского каталога оставляет кириллицу и типографский апостроф и рвёт ярлыки на
соседние проекты. Перенос устраняет причину — невидимый `U+00A0` в пути — навсегда.
Симлинк на старом месте оставлен как страховка для IDE, а не как решение.

**Гипотеза прораба про iCloud проверена и отклонена, а не принята из вежливости.**
Прораб предположил, что сложности из-за синхронизации папки. Три команды
(`find -name "*.icloud"`, `ls -ld ~/Documents`, `du -sh`) показали: проект локальный,
заглушек нет, iCloud к отказам отношения не имеет. Правдоподобная причина, совпадающая
по симптомам с настоящей, — самая дорогая ловушка диагностики: починили бы не ту
болезнь и вернулись бы к тем же граблям.

**`.env` собирает агент через MCP, а не прораб через дашборд.** Оба значения
публичные и всё равно уезжают в бандл (правило 3 `CLAUDE.md`), поэтому
`get_project_url` + `get_publishable_keys` дают их напрямую. Просить прораба лезть в
дашборд за тем, что читается из бандла любым посетителем, — ритуал безопасности без
безопасности. Граница прежняя: `service_role`, пароли и токены интеграций агент не
трогает никогда.

**Порт dev-сервера закреплён `--strictPort`.** 5173 на машине прораба занят
посторонним процессом, и Vite молча переезжал на соседний порт — адрес для приёмки
менялся от запуска к запуску. Молчаливая подмена адреса хуже отказа: прораб открывает
старую вкладку и принимает не то, что собрал агент. Занятый порт обязан падать.

**Права агента открыты: git-операции, `execute_sql` и `apply_migration` — без
подтверждения (постскриптум с3).** Прораб: «мне приходится подтверждать разрешение на
операции в гите… это замедляет работу. Я тебе доверяю». Агент возразил по одному пункту:
`execute_sql` — один инструмент и для `SELECT`, и для `DELETE`, поэтому разрешение
снимает технический барьер на необратимую запись в прод-базу, подтверждённый каноном
часом ранее. Прораб, услышав возражение, выбрал «разрешить всё, включая миграции».

**Канон переписан честно, а не подкрашен.** Соблазн был оставить формулировку «запись
только с разрешения» и считать, что дисциплина агента её удержит, — но правило,
которому не соответствует ни одна настройка, это враньё в документации, а враньё в
правилах хуже отсутствия правила. Новая формулировка — **«Прод открыт, необратимое
объявляется»**: `DELETE`/`UPDATE`/`DROP`/`TRUNCATE` по живым данным агент показывает
текстом ДО исполнения с оценкой числа строк. Это не запрос разрешения — прораб не
обязан отвечать; это гарантия, что необратимое не произойдёт втихую.

**В `ask` осталось два класса действий, и ни один не про доверие.** Восемь необратимых
git-команд (`reset --hard`, `clean`, `restore`, `push --force`, `branch -D`…) — потому
что они уничтожают незакоммиченное, чего не вернёт даже `git revert`; `git clean -fd`
сносит в том числе `.env`. И платные/внешние действия (ветки Supabase, создание
проектов, Edge Functions, `deploy_to_vercel`) — потому что это счёт и инфраструктура
за пределами репозитория, а не скорость работы.

**Ограничение, которое правами не лечится, зафиксировано отдельно.** Часть блокировок
дают не `permissions`, а классификатор auto-mode, смотрящий на смысл команды: так был
отклонён `python3 - <<'PY'`, переписывающий файл. Это не чинится настройками и не
должно — правильный ответ был переключиться на штатные `Read`/`Edit`. Записано, чтобы
следующая сессия не искала несуществующее правило в `settings.local.json`.

## Сессия 4 (2026-08-20) — чистка легаси и аудит архитектуры

**Легаси-Vue удалён из дерева. Решение прораба, отменяющее решение с1.** В с1 было
записано «правила сносим, код оставляем»: 173 файла объявлены мёртвой зоной и
оставлены на диске. В с4 прораб распорядился вычистить их полностью, и это не смена
настроения, а следствие смены задачи: он потребовал аудит архитектуры, а аудит по
дереву, где 88% файлов — мусор, читает мусор. Каждый `grep` вытаскивал бы Vue, каждый
счётчик строк врал, агенты жгли бы контекст на файлах, которых через час не будет.
Агент возражений не имел: код остаётся в git-истории (`git show 4dd010c:src/...`),
то есть это перевод в архив, а не уничтожение.

**Безопасность чистки доказывалась ДО удаления, а не проверялась после.** Три
машинные проверки: ноль импортов живого кода за пределы `src/react`, ноль упоминаний
`.vue` и легаси-каталогов в живом коде и конфигурации, ноль Vue-следов в
`package.json`. Финальное доказательство — после: бандл остался байт-в-байт
(358.76 КБ / 110.29 gzip). Удалённое не участвовало в сборке, значит регресс
невозможен физически, а не маловероятен. **Это образец приёмки для будущих удалений:
цифра, которая не изменилась, доказывает больше, чем зелёная сборка.**

**Правило 7 не удалено, а перевёрнуто.** Соблазн был снести его вместе с мёртвой
зоной — правило описывало то, чего больше нет. Вместо этого оно смотрит вперёд:
«дерево чистое, мусора не заводим; файл, переставший использоваться, удаляется тем
же шагом». Причина: мёртвая зона возникла не по злому умыслу, а потому что «пусть
пока полежит» — и без правила возникнет снова. Синхронизировано в восьми местах;
политика в этом харнессе живёт текстом в файлах правил, субагентах, скиллах и
`gotchas.md`, и правка одного места оставляет семь врущих.

**Бланк с реквизитами вынесен из `public/`, а не удалён.** `public/Exel.xlsx`
содержит расчётный счёт, МФО и ИНН ООО «ARGO MEDIA» и отдавался по прямой ссылке без
авторизации (проверено curl: HTTP 200, 68 397 байт) при публичном GitHub-репозитории.
Удалить было нельзя — как референс печатной формы он ценен: по нему видно, каким
должен быть экспорт. Перенесён в `docs/reference/`. **Общее правило записано в
`gotchas.md` §10: `public/` раздаётся вебом ЦЕЛИКОМ, включая забытое.**

**AUDIT-2026-08-19 переехал в хронику, но сначала был разобран.** Файл дублировал
роли current-state и backlog и лежал в корне как основной документ проекта. Прямое
удаление стоило бы проекту продуктовой очереди: проверка показала, что **семь идей
из разделов P1/P2 не записаны больше нигде** — шаблоны комплектов, дублирование
списка, QR-коды, отчёт по простаивающему, уведомление о невозврате, горячие клавиши.
Вехи 1–6 в roadmap сплошь технические, продуктовых там не было вовсе. Идеи перенесены
в `05-roadmap.md`, раздел «Продуктовая очередь», файл — в `docs/handoffs/` под
номером 0. **Правило на будущее: перед удалением документа — проверить, что в нём
уникального, а не полагаться на ощущение «всё это уже есть».** Одна из семи идей при
переносе оказалась наполовину сделанной (`client_name` и `venue` уже в схеме) и была
переписана по факту — сверка с кодом обязательна и при переносе идей.

**Аудит построен как состязательный, а не как перечисление.** Семь аудиторов по
измерениям, каждый читает весь живой код целиком (5 083 строки — дешевле, чем грепать
фрагменты, и убирает главный источник вранья в аудитах: выводы по кускам). Затем
каждая находка уходит отдельному скептику с брифом «опровергни по реальному коду,
сомневаешься — отклоняй». Отсеялось пять находок: четыре как уже записанные долги,
одна как выдумка без реальной цены. **Смысл конструкции — ложная находка дороже
пропущенной:** она сжигает время прораба и подрывает доверие ко всему отчёту.
Отдельным требованием было назвать и то, что сделано ПРАВИЛЬНО: на вопрос «правильно
ли собран проект» ответ обязан быть честным в обе стороны.

**Приёмку в этой сессии делал агент, а не прораб** — по его прямой просьбе («я не у
мака»). Это отступление от правила разделения проверок, и оно записано как
исключение, а не как новая норма: живой прогон Playwright доказывает, что код
работает, но не что продуктом удобно пользоваться. Долг «прораб открывает приложение
сам» висит третью сессию подряд и в очереди целей сохранён.

## Сессия 5 (2026-08-20 → 21) — выполнение аудита целиком

**Аудит выполнен за одну сессию вместо предложенных шести.** Прораб задал цель
«выполнить всё из проведённого аудита»; компенсация сжатия — отдельный коммит на
каждый шаг с зелёными гейтами, ревью каждого блока архитектором и раздельные
коммиты «поведение отдельно от переноса» на распилах. Все 44 строки таблицы находок
закрыты; хроника — handoff с5.

**Порезка styles.css на @layer отклонена решением агента.** Предусловие исчезло:
после сноса мёртвых классов и схлопывания readability-хвоста файл 779 строк (под
порогом ~800) и каждое правило объявлено один раз. `@layer` при этом инвертирует
приоритет `!important`, а verify-скрипт слоёв не моделирует — риск без выгоды.
Решение обратимо; вернуться, если файл снова перерастёт порог.

**`savedId` удалён, а не сохранён флагом.** После навигации на `/lists/:id/edit`
источником правды становится URL; гвард `savedId` был второй головой HIGH-дефекта
и врал подписью «Сохранено» при простом открытии черновика. Плата: кнопка больше
не пишет «Сохранено» — подтверждение зелёной строкой. Вернуть подпись можно только
честным отдельным флагом.

**«Локация» осталась обязательной.** Все 1481 строки прода заполнены, поле —
словарная норма. Клиент называет поле при пустом вводе; база обороняется
`coalesce(nullif(btrim(...)),'')` → пустое значение сохраняет прежнюю локацию,
а не роняет транзакцию.

**Оптимистическая блокировка — через `errcode 40001`, опциональная.**
`p_expected_updated_at default null`: старый клиент работает без сверки, новый
получает конфликт версий кодом стандартного serialization_failure. Ввод пользователя
при конфликте не сбрасывается — повторное сохранение после предупреждения считается
осознанным решением человека.

**Ключ черновика редактора живёт ВНЕ префикса `equipment-lists:`.** Тот префикс
сбрасывается на каждом create/update/delete/transition — черновик уносило бы чужим
удалением списка. Цена: черновик не чистится общей инвалидацией, только своим
жизненным циклом (создание списка / «Начать заново» / TTL 24 ч / выход из аккаунта).

**Поколения инвалидации кэша — глобальные, не по префиксу.** Инвалидации редкие,
карта префиксов не окупается; цена — изредка невиновный летящий ответ не попадает
в кэш и перезапрашивается. Простота выбрана осознанно.

**Юрлицо в Excel — «ARGO MEDIA» без дефиса.** Частотность в коде 6:1; дефис
встречался один раз в ячейке бланка. Если в уставных документах дефис — правка
одной строки в `documentDefaults.ts`; прораб предупреждён в чеклисте приёмки.

**Риск «immutable на 404 /assets» принят до вехи 2.** Подтверждён живым запросом
к превью: заголовки Vercel ставятся до файловой системы. Грозит только откатом к
байт-в-байт тому же билду; кондиционировать по статусу Vercel не умеет; системное
лечение — обработчик провала чанка в ErrorBoundary (веха 2, следующая в очереди).

**Работа worktree-агента с устаревшей базы выбрасывается, а не сливается.**
Worktree-изоляция срезается с main, а не с ветки сессии (gotchas §13): один прогон
lists-блока пропал целиком, переделан в основном дереве. Слияние поверх устаревшей
базы молча откатило бы коммиты сессии — потеря одного прогона дешевле.

**Приёмку живыми кликами прораб снова делегировал** («что можем — сам протестирую»,
принято без ручного прогона по чеклисту). Чеклист приёмки сохранён артефактом и
остаётся действительным после выкатки — прогон руками не отменён, а отложен.
