# Аудит новых модулей: скорость и вид (с23)

Прогон 15 агентов 2026-08-24: контракт дизайн-системы → 8 срезов (4 перфа, 4 UI)
→ 4 скептика на перф → судья UI → синтез. Перф-находки прошли опровержение,
UI-находки склеены и очищены от вкусовщины. Замеров в браузере НЕ было — всё
добыто чтением кода и объёмами прода.

# 1. ОТВЕТ

**Первой — UI (B). Второй — оптимизация (A), и она честно ужалась до одной сессии.** Но перед обеими есть полдня, которое не относится ни к A, ни к B: четыре находки — это не «медленно» и не «некрасиво», это сломано.

Почему не A: из ~20 перф-находок скептики подтвердили **две**, и обе `low` — `export-fetches-all-employees` (тянем всю таблицу employees ради 1–3 водителей) и `plans-list-intl-per-card` (Intl-форматтеры в теле карточки). Всё остальное — `overstated`. Самая громкая, `full-size-photos-for-36px-avatars`, посчитана по факту прода: 12 фото, средний файл 77 КБ, весь раздел меньше мегабайта — не «3–5 МБ». `fullsize-photo-in-36px-avatar` и `uploads-strictly-serial` описывают фотографии машин, которых в базе **ноль**. `assign-blocks-whole-matrix` — окно ровно в один RTT, и предложенная правка (снять `disabled`) без снятия `if (!planId || addingCell) return` в `useHallPlanEditor.assign` делает клики молча пустыми, то есть хуже. Оптимизировать сейчас — лечить боль, которой на 12 сотрудниках, 6 машинах и 1 плане не существует.

Почему порядок именно такой, а не наоборот. Перф-правки, которые уцелели, живут в трёх местах: `features/*/api.ts` (обёртки `cachedQuery`), инициализатор `useState` на странице и `app/App.tsx` (гейт прогрева). UI-правки живут в `styles.css` и в JSX. Пересечение ровно одно и оно предсказуемое: **тулбар и ветка загрузки трёх списочных страниц**. Если сначала сделать кэш, в тулбар придёт `DataAge`, в ветку загрузки — первый кадр из кэша и флаг `isRefreshing`; потом UI-сессия эту же разметку перепишет второй раз (счётчик по формуле каталога, крестик поиска, скелет вместо `.state-block`). В обратном порядке кэш садится на уже готовую разметку и меняет только начальное значение `useState` плюс добавляет один готовый компонент в готовый тулбар. Одна из двух переделок отпадает.

Работы, которые дешевле одним проходом, а не по категориям:
- **Тулбары трёх списков** — `toolbar-count-divergent`, `search-clear-missing`, место под `DataAge`. Три файла, один заход.
- **Эффект загрузки списка** — `thumbnails-serial-roundtrips` (`Promise.all`) и `new-modules-no-cache` пишутся в одну и ту же функцию; разводить их по сессиям бессмысленно.
- **`styles.css`** — девять несвязанных правок в одном файле на 1132 строки, который сам стоит за порогом распила. Их надо вести близко по времени, иначе получим конфликты в общем листе.
- **`halls.css`** трогают три сессии из семи — держать порядок печать → карточка плана → тач.

Что делать «сначала», хотя об этом не спрашивали: `print-leak` (печать в каталоге ломается после захода в «Залы»), `hall-editor-header-mobile` (на телефоне спрятан статус **«Не сохранилось»** — человек уходит с площадки, уверенный, что план в базе), `mono-input-13px-ios-zoom` (iOS зумит четыре поля и не возвращает), `hall-palette-contrast` (три цвета из восьми не держат контраст с белым: 3,30 / 3,55 / 3,71 при нужных 4,5 — на ТВ имя зала не читается). Это не полировка, это отказы.

# 2. КАРТИНА ПО ПЕРФУ

- Измеримо не болит ничего. Ни одного подтверждённого узкого места: подтверждены две находки размером `S` с влиянием `low`.
- Мифы: полноразмерные фото (реально 77 КБ, весь раздел 922 КБ), «три круга до миниатюры» (миниатюра — украшение, список уже нарисован после первого круга; `getSignedUrls` при полном попадании выходит до сети), последовательная загрузка файлов (в проде 0 сканов и 0 фото машин), «ТВ-поллинг перерисовывает всё» (данные идентичны — React не трогает DOM), «матрица ждёт справочник позиций» (6 строк, физически не самый медленный из четырёх параллельных запросов).
- Единственный системный пробел — **у трёх новых модулей нет `persistentCache`**: `readCachedQuery` встречается в `equipment/*` и `lists/*` и ни разу в `employees`/`vehicles`/`halls` (кроме `fetchEmployeeBriefs`). Цена — не скорость, а мигание скелетона ~200–400 мс на каждом «сохранил → назад». Это выравнивание по дому, а не оптимизация.
- Два дешёвых системных выигрыша вне модулей: `prefetch-unconditional-heavy` — `AppShell` безусловно качает `fetchAllEquipment` (~1.4 МБ JSON) через 700 мс после входа в **любой** раздел; `index-html-priorities` — в `index.html` нет `preconnect` к домену Supabase, хотя адрес известен на сборке. Одна строка разметки и один `if` по маршруту.
- Мина, которую надо назвать вслух: `fetchEmployees` в `features/employees/api.ts` делает `select('*')` — паспорт, ПИНФЛ, адрес прописки. Когда его будут заворачивать в `cachedQuery`, только `{ persist: false }`. Иначе ПДн всех сотрудников лягут в `localStorage`.

# 3. КАРТИНА ПО UI

- Главный системный дефект один и повторяется шесть раз: **вместо канонического примитива взят соседний, «примерно похожий»**. `.state-block` (примитив пустоты и ошибки) в ветке загрузки четырёх экранов вместо скелета; `.field-hint` (11px подсказка под полем) вместо `.form-success`/`.form-error` для исхода операции; `.employee-avatar` (круг 36px) и `.employee-photos` (портрет 92×116) на фотографиях машин; `.mono` с `font-size: 13px !important` на инпуте, хотя дом уже обходил эту мину классом `.plate-badge`; проценты пятиколоночного каталога на четырёхколоночных таблицах; копия `.list-card` своими именами в `halls.css`, уже разъехавшаяся по метрикам.
- Модули выглядят недоделанными в четырёх конкретных точках, а не «в целом»: пустая белая коробка 260px вместо страницы при загрузке, пять системных `input[type=file]` (правил под файловый инпут в `styles.css` нет вообще — контрол рисует браузер, по-узбекски он всё равно скажет «Choose File»), ответ формы (вопрос про тёзку, ошибка сохранения) печатается на два экрана ниже единственной кнопки «Сохранить», и погашенная кнопка, которая не говорит, чем её оживить.
- Три механизма дома не дотянулись до новых модулей: `useDocumentTitle` стоит ровно в одном месте (`HallPlanPage`) — три вкладки подписаны одинаково «ARGO · Учёт оборудования»; крестик очистки поиска есть только в `EquipmentPage`; `DataAge` — на двух списках из шести.
- Один настоящий пробел контракта, шире новых модулей: `lib/useModalLayer.ts` вешает только Escape и блокировку прокрутки. Ни ловушки фокуса, ни возврата фокуса на триггер — при объявленном `aria-modal="true"`. Это все девять дроверов системы, включая старые.

# 6. ЧЕГО НЕ ДЕЛАТЬ

- **`editor-object-kills-memo`** — переписывать шов `useHallPlanEditor` (стабилизировать ~15 функций, обернуть клетки в `React.memo`, который в проекте не используется нигде) ради 8 существующих ячеек и потолка в 300. Размер `L`, выигрыш невидим.
- **`full-size-photos-for-36px-avatars`, `fullsize-photo-in-36px-avatar`** — второй вариант снимка в бакете или платные Image Transformations ради файлов по 77 КБ и фотографий машин, которых нет. Страховка на вырост стоит одной константы: `MAX_SIDE` в `lib/compressPhoto.ts`. Строка в `backlog.md`.
- **`uploads-strictly-sequential`, `uploads-strictly-serial`** — последовательность даёт по-файловый статус и кнопку «Повторить» для упавшего; при пуле воркеров это придётся городить заново. Сжатие сканов паспорта — прямо запрещённое решение (комментарий в `compressPhoto`: мелкий шрифт становится нечитаемым).
- **`assign-blocks-whole-matrix` в предложенном виде** — оптимистичная ветка замены спорит с решением, записанным комментарием над `assign`. Максимум допустимого — гасить одну клетку вместо доски, и только вместе с решением судьбы `if (!planId || addingCell) return`. Обсуждать в сессии 6, не в перф-сессии.
- **`tv-poll-repaints-everything` в части «поллить только `fetchHallAssignments`»** — сломает витрину: `cellMap` строится по `halls × positions`, ячейка с неизвестным `hall_id` не отрисуется никогда, новый зал на ТВ не появится. Осмысленный остаток — не звать `setState` при равенстве ответа; это косметика, не сессия.
- **`catalog-gates-first-frame`** — не подтверждается: четыре запроса уходят одновременно, справочник из 6 строк не бывает самым медленным.
- **`namesake-check-doubles-save-wait` в части «параллельно с save»** — проверка гейтит сохранение, параллельный запуск покажет предупреждение после записи в базу. Допустимо только «не гонять, если ФИО и дата рождения не менялись», и это ~200 мс на редком действии.
- **`card-files-two-round-trips-and-refetch`, `drawer-refetches-files-every-open`** — кэш строк `employee_files`/`vehicle_files` опасен: после загрузки фото форма уходит в карточку, которая обязана показать только что залитое.
- **`trim-storage-parses-everything`, `invalidate-leaves-pending`** — механизмы реальны, цена низкая, окно ошибки — время жизни одного запроса. `pendingLoads` почистить попутно в сессии 7, `trimStorage` — в backlog.
- **`edit-page-cold-load-of-known-row`** — передача строки через `state` роутера вводит риск `last-write-wins` поверх чужой правки (оптимистичной блокировки в `updateEmployee` нет), а «Загружаем файлы…» всё равно останется. Не окупается.
- **`phone-not-tappable` в части нормализации номеров** — это правка данных в проде, а не вёрстки. `tel:`-ссылки сделать можно (сессия 4), нормализацию выносить отдельной задачей с предварительным `SELECT`.
- Не заводить toast, модалку-примитив, UI-кит и `React.memo` как практику. В доме их нет осознанно, а пять рантайм-зависимостей — позиция, а не случайность.

# 7. ЧТО ОСТАЛОСЬ НЕПРОВЕРЕННЫМ

- **Ни одного реального замера.** Все перф-выводы — чтение кода плюс объёмы строк из прода. Нет Lighthouse, нет профиля Performance, нет водопада Network, нет RUM. Ни один заявленный «тормоз» не воспроизведён на живой странице; цифры сборки взяты из build-лога, а не из браузера.
- **Контраст палитры** посчитан арифметически по хексам. Как эти три цвета выглядят на конкретной панели в зале, с её яркостью и цветопередачей, с пяти метров — не проверял никто.
- **Устройства.** iOS-зум на `.mono`, тач-цели в матрице, поведение планшета на площадке, `env(safe-area-inset-bottom)` — вывод из CSS, а не из рук. Первое, что стоит проверить прорабу физически.
- **Печать** читалась как CSS, а не как лист. Утечка правил и поведение `@page` — обоснованная гипотеза, доказательство — два Ctrl+P в одной вкладке.
- **Узбекский.** Проверялось только наличие пары в `tr(ru, uz)`. Качество и **длина** узбекских строк не читались — а длинные подписи ломают ровно те тулбары, кнопки и подписи галок, которые правятся в сессиях 2 и 3.
- **Доступность.** Скринридером никто не ходил. `aria-live` для результатов действий нет, связи поля с текстом ошибки нет, «таблица-карточки» на телефоне для скринридера не существует как таблица — заголовки уходят в `content: attr(data-label)`.
- **Тариф Supabase Storage** (есть ли Image Transformations) не проверялся. Для принятых решений это неважно — аватарки чинить не надо, — но если решите иначе, это первый вопрос.
- **Права и RLS не аудировались вовсе** — тема была перф и вид. Сессия 7 кладёт выборку сотрудников в кэш: перед её закрытием нужен явный прогон, что `{ persist: false }` стоит и `setCacheScope` чистит кэш при смене пользователя, иначе второй сотрудник на общем компьютере увидит чужие данные из памяти вкладки.
- **Модуль vehicles на реальных данных глазами не видел никто:** `vehicle_files` пуста, то есть весь фото-путь (список, дровер, галерея, экспорт) в проде ни разу не отрабатывал на настоящем снимке.

### `full-size-photos-for-36px-avatars` — Список сотрудников качает полноразмерные фото ради аватарки 36×36

Второй путь заодно снимает скачивание оригиналов в loadEventPhotos: 320 px — ровно то, что нужно документу.

Но цифры аудитора выдуманы. Замер по проду (storage.objects ∩ employee_files): kind='photo' — 12 файлов, средний 77 КБ, максимум 108 КБ, ВСЕГО 922 КБ. Аргумент «на 100 — десятки МБ» перевёрнут: loading="lazy" как раз и делает цену независимой от длины списка — платим за ~15 видимых строк, а не за 100. Про экспорт тоже мимо: loadEventPhotos качает те же 77 КБ на портрет в три потока с прогрессом, это разовое явное действие. Риск на вырост реальный (снимок прямо с телефона в 1600 px даст 400–700 КБ), но лечится он одной константой MAX_SIDE, а не введением второго варианта в бакете; серверные трансформации Supabase — платный тариф. Сегодня — не узкое место.

### `namesake-check-doubles-save-wait` — «Сохранить» в карточке сотрудника всегда ждёт лишний запрос про тёзок
- **срез:** perf-employees · **вердикт:** overstated · **влияние:** low · **размер:** S
- **файлы:** src/react/features/employees/EmployeeFormPage.tsx (handleSubmit), src/react/features/employees/api.ts (findNamesakes)
- **симптом:** Нажал «Сохранить изменения» — кнопка думает заметно дольше, чем должна: два ожидания сети подряд вместо одного. При правке телефона у давно заведённого человека это ожидание вообще ни за чем.

Проверка вдобавок стоит на критическом пути: пока она летит, запрос на сохранение ещё не стартовал.
- **правка:** Убрать проверку с критического пути. Минимум: в режиме правки не гонять findNamesakes, если last_name/first_name/birth_date не отличаются от загруженной карточки (держать снимок исходных значений рядом с draft). Лучше: запускать проверку в фоне по onBlur полей фамилии/имени/даты — к моменту нажатия «Сохранить» ответ уже на руках, и сохранение уходит первым же кругом. Заодно убрать мигание подписи кнопки: setIsSaving(false) в finally проверки срабатывает прямо перед тем, как save() снова поднимет флаг.

Но цена — ОДИН запрос на 10 строк с двумя ilike и neq по id, то есть ~200 мс поверх сохранения, на действии, которое по комментарию в api.ts делают «редко и по одному человеку». Параллелить с save() нельзя по смыслу: проверка гейтит сохранение (found.length>0 → return и показ предупреждения), запусти её параллельно — и предупреждение прилетит уже после записи в базу, то есть находка предлагает сломать принятое поведение. Единственная безопасная правка — пропускать проверку в режиме правки, когда фамилия/имя/дата рождения не менялись относительно загруженной строки. Экономия ~200 мс на редком действии — это low.

### `uploads-strictly-sequential` — Файлы карточки грузятся строго по одному, сжатие фото — в главном потоке
- **срез:** perf-employees · **вердикт:** overstated · **влияние:** low · **размер:** M
- **файлы:** src/react/features/employees/EmployeeFormPage.tsx (runUploads), src/react/lib/compressPhoto.ts (compressPhoto), src/react/features/employees/eventExport.ts (loadEventPhotos — образец с DOWNLOAD_CONCURRENCY)
- **симптом:** Заводят сотрудника с фото и четырьмя сканами паспорта — очередь ползёт по одной строке, «Загружаем…» переезжает с файла на файл, на мобильном канале это минуты. В момент подготовки фото интерфейс подлипает.
- **механизм:** runUploads — это for...of с await внутри: следующий файл не стартует, пока не лёг предыдущий, конкурентность жёстко равна единице. При этом рядом, в eventExport.loadEventPhotos, тот же дом уже гоняет три воркера (DOWNLOAD_CONCURRENCY = 3). Сканы через compressPhoto не проходят вовсе (сжимается только kind === 'photo'), то есть PDF или JPEG паспорта уезжает в бакет целиком — до 10 МБ. Сжатие фото делается на главном потоке: createImageBitmap + drawImage + toBlob, и на 8-мегапиксельном снимке это заметный кадровый провал.
- **правка:** 1) Дать очереди ту же схему воркеров, что в loadEventPhotos: 2–3 файла параллельно, статусы в setUploads обновляются как есть (они уже по id). 2) Развести сжатие и отправку: пока предыдущий файл летит в бакет, следующий уже жмётся. 3) Разгрузить главный поток — createImageBitmap(file, { resizeWidth, resizeHeight, resizeQuality: 'high' }) масштабирует на стороне декодера, а сам canvas-проход можно унести в OffscreenCanvas внутри воркера.
- **скептик:** Факт последовательности верен: runUploads — for...of с await, конкурентность 1, рядом в eventExport.loadEventPhotos действительно DOWNLOAD_CONCURRENCY=3. Дальше начинаются натяжки. (1) «Сжатие в главном потоке — заметный кадровый провал» — не подтверждается кодом: тяжёлые шаги compressPhoto это createImageBitmap (декод вне главного потока — ровно поэтому он и выбран вместо <img>) и canvas.toBlob (кодирование асинхронное); на главном потоке остаётся drawImage. Плюс в этот момент человек смотрит на экран успеха с UploadQueue, а не редактирует что-то — джанк там некому заметить. (2) «Сканы уезжают целиком до 10 МБ» подан как дефект, хотя это записанное решение: шапка compressPhoto прямо говорит, что мелкий шрифт паспорта от пережатия становится нечитаемым, а PDF браузер не декодирует. Правка «сжимать сканы» сломала бы принятое поведение. (3) Объём: очередь по EmployeeFileFields — несколько фото плюс максимум 4 скана; в проде сканов не загружено НИ ОДНОГО (employee_files: только 12 photo), фото весят 77 КБ. Действие разовое на карточку. Последовательность к тому же держит понятный по-файловый статус и «Повторить». Экономия есть, но это low.

### `card-files-two-round-trips-and-refetch` — Файлы в карточке ждут двух кругов подряд и перезапрашиваются на каждое открытие
- **срез:** perf-employees · **вердикт:** overstated · **влияние:** low · **размер:** M
- **файлы:** src/react/features/employees/EmployeeDrawer.tsx (useEffect по employee.id), src/react/features/employees/EmployeeFormPage.tsx (эффект загрузки existingFiles), src/react/features/employees/api.ts (fetchEmployeeFiles)
- **симптом:** Открыл карточку — «Загружаем файлы…», закрыл, открыл ту же снова — снова «Загружаем файлы…». В разделе так и работают: пробегают по нескольким людям и возвращаются к первому.
- **механизм:** В дровере isLoading снимается в .finally, а внутри .then стоит await getSignedUrls(...) — то есть надпись «Загружаем файлы…» держится оба круга: и запрос строк employee_files, и подпись ссылок. В форме правки то же самое: filesState переводится в 'ready' только после getSignedUrls. Кэша у fetchEmployeeFiles нет (в отличие от списков в lists/api.ts), поэтому повторное открытие той же карточки — снова оба круга; подписи-то из signedUrlCache возьмутся мгновенно, а строки нет.

Кэша у fetchEmployeeFiles действительно нет. ### `prefetch-unconditional-heavy` — Прогрев в AppShell тянет ~2 МБ каталога и картинок на каждом старте — даже когда человек пришёл в «Сотрудников» или в план залов

Реальная цена: ~1.4 МБ фонового трафика на перезагрузку у человека, которому каталог сейчас не нужен. Правку (гейт по маршруту) делать стоит, но это medium.

### `thumbnails-serial-roundtrips` — Миниатюры сотрудников и машин доезжают через три последовательных круга сети вместо двух
- **срез:** perf-core · **вердикт:** overstated · **влияние:** low · **размер:** S
- **файлы:** src/react/features/employees/EmployeesPage.tsx (EmployeesPage, эффект загрузки), src/react/features/vehicles/VehiclesPage.tsx (VehiclesPage, эффект загрузки)
- **симптом:** Список уже нарисован, а на месте фото ещё секунду висят серые кружки — и это заметно именно потому, что строки уже пришли и человек начал их читать.

Но цена ошибки — один лишний RTT на УКРАШЕНИИ строки: список уже отрисован после первого запроса, задерживаются только миниатюры, и по коду это осознанно ('миниатюры — украшение строки: их отказ не должен ронять список'). Плюс lib/signedUrlCache.ts держит подписанные ссылки в памяти вкладки на 55 минут, так что третий круг на повторных монтажах не повторяется — платится только выборка фото. На 12 сотрудниках и 6 машинах человек этого не увидит; правка на 5 строк (Promise.all) полезна, но medium она не тянет.

### `trim-storage-parses-everything` — persistentCache на каждой записи разбирает весь localStorage — как только записей станет больше 64, ввод начнёт спотыкаться
- **срез:** perf-core · **вердикт:** overstated · **влияние:** low · **размер:** S
- **файлы:** src/react/lib/persistentCache.ts (trimStorage, writeEntry)
- **симптом:** Набор в строке поиска каталога начинает подтормаживать пачками: после каждого ответа сервера кадр «проглатывается». Чем дольше человек пользуется системой, тем стабильнее эффект — он не проходит после перезагрузки, потому что записи лежат в localStorage.
- **механизм:** writeEntry на каждую успешную запись зовёт trimStorage, а тот, перевалив MAX_PERSISTED_ENTRIES = 64, делает JSON.parse ПОЛНОГО значения каждой записи — только ради поля touchedAt. Среди записей есть тяжёлые: equipment:model-units:[...] на модель с 596 единицами и select('*'), страницы equipment-lists, составы списков. Разбор идёт синхронно в главном потоке. Порог 64 переступается сам собой и навсегда: ключ страницы каталога включает строку поиска (equipmentModelsCacheKey), плюс предзагрузка следующей страницы — то есть примерно две записи на каждый поисковый запрос, а просроченные записи из localStorage не удаляются ничем, кроме этого же trimStorage.
- **правка:** Не разбирать значения ради метаданных: держать один служебный ключ-индекс `<scope>:__index` с картой {ключ: touchedAt} и подрезать по нему; либо вынести touchedAt в имя ключа. Заодно выметать записи с истёкшим expiresAt, а не только сверх лимита — тогда порог перестанет быть постоянно взведённым. Проверить дёшево: в консоли посчитать Object.keys(localStorage).filter(k => k.startsWith('argo-warehouse:v4:')).length на рабочей машине прораба.
- **скептик:** Код такой, как описано (persistentCache.ts: writeEntry → trimStorage, ранний выход при ownedKeys.length <= 64, дальше JSON.parse каждой записи). Но 'ввод начнёт спотыкаться' — не про этот механизм. (1) trimStorage вызывается на ЗАПИСИ, то есть после ответа сети, а не на нажатии клавиши; поиск каталога вдобавок дебаунсится 350 мс (EquipmentPage.tsx строки 218-225), так что записей примерно две на завершённый поиск, а не на символ. (2) Самая тяжёлая запись из перечисленных в кэш вообще не попадает: fetchAllEquipment (~1.4 МБ) стоит persist:false и живёт только в памяти. (3) Разбор ограничен сверху квотой localStorage (~5 МБ) и, что важнее, тем, что trim держит ровно 64 записи — то есть на каждой записи парсится 65 штук, а не растущая куча. Реальный худший случай — разовая синхронная пауза десятков миллисекунд после ответа сети у человека, который наработал 30+ разных поисковых запросов. Чинится дёшево (хранить touchedAt в имени ключа), но это low, не medium.

### `invalidate-leaves-pending` — invalidateCachePrefix чистит кэш, но не запросы в полёте — сразу после сохранения можно получить дореформенный ответ
- **срез:** perf-core · **вердикт:** overstated · **влияние:** low · **размер:** S
- **файлы:** src/react/lib/persistentCache.ts (invalidateCachePrefix, cachedQuery), src/react/features/employees/api.ts (updateEmployee, setEmployeeDocumentPhoto)
- **симптом:** Редкая, но неотлаживаемая картина: сотрудника переименовали, а пикер клетки в плане залов (или пикер водителя) показывает старое ФИО — и показывает его до перезагрузки страницы, потому что в кэш ответ так и не лёг.
- **механизм:** invalidateCachePrefix поднимает cacheGeneration и вычищает memoryCache с localStorage, но карту pendingLoads не трогает — её очищает только setCacheScope при смене пользователя. Запрос, стартовавший ДО инвалидации, остаётся в pendingLoads, и следующий вызов cachedQuery без bypass присоединяется к нему (`const pending = pendingLoads.get(key); if (pending) return pending`) — получает данные, снятые до сохранения. Записать их в кэш он тоже не может: проверка `generation === cacheGeneration` уже не проходит. Вторая половина того же места: поколение ГЛОБАЛЬНОЕ, поэтому любая инвалидация по одному префиксу отменяет запись в кэш всем летящим в этот момент загрузкам, включая прогревочные из AppShell, — прогрев тихо пропадает впустую.
- **правка:** В invalidateCachePrefix удалять из pendingLoads ключи с тем же префиксом (тогда следующий вызов пойдёт за свежими данными, а не присоединится к устаревшему). Поколение сделать по-префиксное — Map<prefix, number> — либо сверять не номер поколения, а метку последней инвалидации, попавшей в префикс ключа, чтобы чужой сброс не отменял запись соседних загрузок.
- **скептик:** Оба факта в persistentCache.ts верны: invalidateCachePrefix поднимает cacheGeneration и чистит memoryCache и localStorage, но pendingLoads не трогает (её чистит только setCacheScope), а cachedQuery без bypass присоединяется к висящему промису. Однако окно ошибки — это ровно время жизни одного запроса: .finally у load удаляет ключ из pendingLoads, как только запрос сел. Чтобы получить дореформенный ответ, нужно, чтобы кэшируемая выборка летела ИМЕННО в момент прихода ответа на запись. У новых модулей кэшируемая выборка сейчас одна (fetchEmployeeBriefs — пикер водителей и клетки залов), а возврат на список после правки идёт через некэшируемый fetchEmployees, то есть свежий. Вторая половина (глобальное поколение отменяет запись в кэш всем летящим загрузкам, включая прогрев) подтверждена по коду, но её цена — потерянный прогрев в редком совпадении 'сохранение в первые секунды после старта вкладки'; данные при этом отдаются вызвавшему корректные, просто не кэшируются. Механизм есть, влияние — low.

### `index-html-priorities` — index.html: приоритетным preload идёт картинка страницы входа, а к домену данных нет preconnect
- **срез:** perf-core · **вердикт:** overstated · **влияние:** low · **размер:** S
- **файлы:** index.html, src/react/lib/supabase.ts
- **симптом:** У вошедшего человека (а это все, кроме первого раза) на каждой холодной загрузке скачивается 69 КБ иллюстрации, которую он не увидит; при этом первый запрос к базе начинает с нуля искать DNS и жать TLS-рукопожатие — на телефоне это лишние 200–300 мс до первых данных.
- **механизм:** В <head> стоит `<link rel="preload" href="/illustrations/av-warehouse.webp" as="image">` — 69 КБ с высоким приоритетом. Этот файл используется в LoginPage и в одной плитке HomePage; в /employees, /vehicles, /halls он не нужен, но качается всё равно, конкурируя с чанками приложения. Обратная сторона: подключения к домену Supabase (VITE_SUPABASE_URL) браузер не может начать раньше, чем выполнится и инициализируется бандл, — ни preconnect, ни dns-prefetch в разметке нет, хотя адрес известен на этапе сборки.
- **правка:** Добавить `<link rel="preconnect" href="https://<project>.supabase.co" crossorigin>` (адрес подставлять из VITE_SUPABASE_URL плагином трансформации HTML в vite.config.ts, чтобы он не разъехался с окружением). Preload иллюстрации либо снять, либо оставить только для входа — на /login она и так грузится с loading="eager" fetchPriority="high" из самого компонента.
- **скептик:** Первая половина рассыпается на двух проверках. (1) 'Высокий приоритет' — неверно: <link rel=preload as=image> без fetchpriority получает у Chrome низкий/средний приоритет и планируется ПОСЛЕ рендер-блокирующих скриптов и CSS; проверил dist/index.html — modulepreload на react-vendor/supabase и stylesheet стоят ниже по разметке, но именно они идут первыми по приоритету. (2) 'Качается всё равно' — верно только на первом визите: vercel.json отдаёт /illustrations/(.*) с `max-age=604800, stale-while-revalidate=86400`, то есть неделю без единого запроса, а картинка реально нужна и на /login, и на плитке HomePage (grep: LoginPage.tsx:68, HomePage.tsx:20) — то есть на самой частой точке входа она не мусор. Остаётся вторая половина, и она честна: ни preconnect, ни dns-prefetch к VITE_SUPABASE_URL в index.html нет, хотя адрес известен на сборке, — это одна строка разметки и экономия DNS+TCP+TLS перед первым запросом данных. Одна валидная строка правки, не 'medium'.
