# 02-features — ARGO Warehouse

Что умеет продукт и **кто что решает — база или браузер**. Ссылки на код — именем файла
и функции; номеров строк здесь нет намеренно, они рвутся любым коммитом.

## 0. Как читать эту страницу

**Схема лежит в репозитории** — выписка прода в
`supabase/migrations/00000000000000_baseline_remote_schema.sql`, машинное представление
в `src/react/lib/database.types.ts`, клиент типизирован (`createClient<Database>`).
Утверждение «у таблицы есть колонка X» здесь — про схему, а не про догадку по типу.

**Вся поверхность обращений клиента к базе — три таблицы и четыре RPC:**
`equipment`, `equipment_lists`, `equipment_movements`; `create_equipment_list_document`,
`update_equipment_list_document`, `update_equipment_model_and_unit`,
`count_equipment_model_units`. К `public.users` клиент не обращается ни разу.

**Почти всякое чтение идёт через `lib/persistentCache.ts`** — память плюс `localStorage`
с ключами `argo-warehouse:v4:<id пользователя>:<ключ>`. Экран сначала рисуется из кэша,
потом обновляется с сервера. Три свойства этого кэша, без которых поведение экранов
читается неверно:

- **Первый кадр не рисует протухшее.** `readCachedQuery` сверяет срок — просроченная
  запись для синхронного чтения равна пустоте. Иначе экран мог нарисовать сколь угодно
  старые данные, а TTL ограничивал бы только повторный запрос.
- **Ошибки «разлогинило / прав нет» проходят наружу.** `cachedQuery` не подменяет старым
  значением ответы с `401`, `PGRST301`, `42501`. Всякую другую ошибку при наличии записи
  он гасит и до UI **не доносит**.
- **Кэш принадлежит человеку.** Смена пользователя сбрасывает память и запросы в полёте,
  выход стирает ключи ушедшего.

## 1. Вход и сессия

| Решение | Кто принимает |
|---|---|
| Существует ли учётная запись, верен ли пароль | Supabase Auth |
| Является ли владелец JWT сотрудником, какая у него роль | БД, `private.is_app_member()` / `private.has_any_role()` |
| Пускать ли на маршрут | КЛИЕНТ, по факту наличия объекта сессии |
| Куда вернуть после входа | КЛИЕНТ, путь из `state.from` |

**Клиент про роль не знает ничего.** Гвард маршрутов — это проверка «сессия вообще
есть», не проверка права. Почему иначе нельзя и почему `revoke` на `public.users`
не надо «чинить» — `01-product` §2 и `03-data-model` §3.

**После входа человек попадает туда, куда шёл.** `LoginRedirect` кладёт полный путь
(`pathname + search + hash`) в `state.from`. Внутренним считается только `/…`: `//host`
браузер читает как чужой сайт, поэтому проверка стоит **дважды** — при записи и при
чтении, потому что `state` истории правится из консоли.

**До ответа Auth не показывается ни одна страница:** пока `getSession()` не разрешился,
`isLoading = true` и рисуется полноэкранный `AppLoader` вместо роутера.

**Отказные ветки.**

| Ситуация | Что происходит |
|---|---|
| Нет `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` | **Сборка падает** гейтом окружения (`vite.config.ts`) и до прода не доезжает. Осталось только для `npm run dev`: форма входа отдельно говорит «Приложение не настроено: нет связи с сервером данных» — а не «неверный пароль» |
| Неверный пароль / сеть лежит | Одно и то же сообщение, ветки **не различаются** |
| Пользователь есть в Auth, но нет в `public.users` | Вход **проходит**, интерфейс открывается, а каждый запрос отсекается RLS → пустые экраны. Отдельного «вы не сотрудник» нет |
| Сессия истекла посреди работы | Редирект на `/login` либо общее «Не удалось загрузить» — что раньше, определяется гонкой и в коде не задано |

## 2. Главная

Три плитки: «Оборудование», «Списки оборудования», «Сотрудники» (заглушка «Скоро»).
База не участвует — страница статическая. Все три — `<article>`: тело кликается
растянутой внутренней ссылкой, а «＋ Создать список» на плитке списков — **отдельная**
ссылка, потому что вложить `<a>` в `<a>` нельзя.

Побочно здесь начинается прогрев: таймеры подтягивают чанки всех страниц, первую
страницу каталога и реестра, затем весь каталог, справочник и картинки. Размер страницы
прогрев не вычисляет сам, а спрашивает у фичи — он входит в ключ кэша, и вторая копия
формулы разошлась бы (`04-architecture` §4).

## 3. Каталог оборудования

**Всё состояние экрана живёт в АДРЕСЕ** (с11): `q`, `type`, `subtype`, `status`, `page`,
`item`. Следствия: возврат из формы заведения и F5 не теряют место, ссылку на позицию
можно переслать, а жест «назад» на телефоне закрывает карточку вместо ухода из раздела.
Локальным остался только `searchInput`.

| Решение | Кто |
|---|---|
| Какие строки видны вообще | БАЗА, RLS `equipment_select_for_members` |
| Отбор, сортировка, окно страницы, `total` | БАЗА (PostgREST) |
| Списки категорий и подкатегорий | БАЗА через `fetchEquipmentTaxonomy` (батчи по 1000, кэш 24 ч) |
| `tracking_mode`, `inventory_code`, «есть ли серийный номер» | КЛИЕНТ, разбором строки `serialnumber` |
| Подпись статуса и её цвет | КЛИЕНТ, словарём кодов (`availability.ts`) |
| Код `EQ-XXXXXX` | КЛИЕНТ, первые 6 символов uuid |
| Картинка позиции | КЛИЕНТ, статический словарь `generated/equipmentImages.ts` |

**Размер страницы — 50 на десктопе и 8 на телефоне** (граница — `lib/breakpoints.ts`);
смена ширины окна пересчитывает размер и сбрасывает номер страницы. На телефоне вместо
пагинации — «Показать ещё N», и она **пересчитывает** страницы 1…N через `Promise.all`,
а не накапливает: инкрементальный `append` даёт двойную вставку в StrictMode и хвост от
прошлого фильтра, если тот сменился пока запрос летел.

**Поиск.** Дебаунс 350 мс, в адрес уезжает с `replace` (иначе каждая буква оставляла бы
запись в истории). Обратная синхронизация идёт через `pushedSearchRef`: без него
собственная запись дебаунса, прилетающая через 350 мс, затирала бы буквы, набранные за
это время. Строка режется по пробелам, берётся **не более шести терминов**; каждый
добавляет свой `.or(...)` по пяти колонкам (`model`, `brand`, `serialnumber`, `type`,
`subtype`). Внутри термина колонки по ИЛИ, между терминами PostgREST складывает по И.
Седьмое слово молча игнорируется.

**Ключ кэша всегда содержит все поля фильтра** (пустыми — `''`), поэтому прогрев без
фильтров и страница без фильтров читают одну запись. Прогретый первый кадр читается
ТОЛЬКО для нетронутого каталога (`page=1`, ни одного фильтра): под фильтром кэш без
фильтра отвечал бы не на заданный вопрос, и честнее скелет.

**Пустое состояние различает причину.** Пустой ответ при поиске или фильтре — «Ничего не
найдено»; пустой ответ **без** запроса и фильтров — «Каталог пуст или недоступен…
обратитесь к администратору склада»: у сотрудника без строки в `public.users` RLS отдаёт
ноль строк, и это не «не найдено».

**Номер страницы зажимается на рендере** (`Math.min(page, pageCount)`), и зажатое
значение и рисуется, и грузится. Иначе после сокращения выборки выходила «Страница 3
из 1» с пустой таблицей.

**Карточка перечитывается с сервера при открытии.** Каталог отдаёт строку возрастом до
десяти минут; drawer при монтировании зовёт `fetchEquipmentById` в обход кэша. Смысл
двойной: сжать окно, в котором устаревшая вкладка перезапишет чужую правку, и получить
актуальный `updated_at` для сверки версии (§4). Перечитанная строка обновляет только
свою строку в таблице. Зависимость эффекта — только `item.id`, иначе он зациклился бы на
собственном обновлении.

Отказ перечитывания **не выдаётся за «данных нет»** — у карточки три состояния: `fresh`,
`stale` («показаны данные из каталога») и `missing` («записи больше нет в базе»). Ответ,
пришедший после закрытия, игнорируется — иначе он заново открыл бы закрытый drawer.

**Отказные ветки.**

| Ситуация | Что видит пользователь |
|---|---|
| Ошибка сети, кэша нет | Блок «Ошибка загрузки» с кнопкой «Повторить» |
| Ошибка сети, кэш есть и не просрочен | **Ничего.** Молча показываются данные до 10 минут давности |
| Протух токен / отказ RLS при тёплом кэше | Ошибка **доходит** до страницы → «Ошибка загрузки» |
| Отказ RLS в виде пустой выборки | Тот же экран «Ничего не найдено», без объяснения |

## 4. Редактирование позиции (drawer каталога)

Две группы полей: «Данные модели» (бренд, модель, категория, подкатегория, длина,
характеристики, описание) — **изменятся у всех экземпляров с тем же брендом и моделью**,
и подпись честно об этом предупреждает; «Конкретная единица» (статус, локация, серийный
номер, количество).

Черновик формы держится одним объектом, чтобы сброс к записи был одной операцией. Пока
идёт правка, черновик **не пересобирается** из пришедшей записи: перечитывание карточки —
в том числе после конфликта версий — не имеет права стереть введённое.

| Решение | Кто |
|---|---|
| Право редактировать | БАЗА, дважды: RPC и RLS |
| **Не изменили ли карточку с момента открытия** | БАЗА, сверкой `updated_at`, errcode `40001` |
| Обязательность бренда/модели/категории/подкатегории | БАЗА **и** клиент |
| Допустимость статуса, `count >= 0` | БАЗА |
| Какие строки считать «той же моделью» | БАЗА, `lower(btrim(brand))` + `lower(btrim(model))` |
| Непустая локация | БАЗА **и** клиент; пустое значение не затирает прежнее (`coalesce(nullif(btrim(...), ''), e.location)`) |
| Сколько единиц затронуто — и до, и после сохранения | БАЗА (`count_equipment_model_units` и `updated_model_units` в ответе RPC) |

RPC делает два `update`: общие поля — по нормализованному совпадению бренда и модели,
поштучные (`availability`, `location`, `count`) — только по `id`. Триггер
`trg_equipment_movement_history` на изменение `count`/`availability` пишет строку в
`equipment_movements`.

### 4.1. Конфликт версий

Правка «данных модели» задевает **все** единицы группы, поэтому устаревшая вкладка была
дорогой ошибкой. Теперь drawer при открытии получает свежий `updated_at`, шлёт его как
`p_expected_updated_at`, и расхождение отменяет правку **целиком** — ни одно поле не
записано, код `40001`. Клиент отличает этот код от любого другого отказа и показывает
своё сообщение, **не сбрасывая форму**; карточка перечитывается фоном, и повторное
сохранение проходит.

`null` в `p_expected_updated_at` значит «сверить нечем» и проверку выключает — путь для
старого клиента, оба новых аргумента имеют default.

### 4.2. Количество серийной карточки не отправляется

Поле «Количество» у серийной позиции заблокировано и показывает `1`, но раньше эта
единица **уезжала** в базу. Триггер реагирует на изменение `count`, и запись с
фактическим количеством ≠ 1 получала фантомную строку «Изменено количество» в журнале —
при правке одного только описания. Теперь параметр не отправляется вовсе
(`count: … ? count : undefined`, `supabase-js` выбрасывает `undefined` из тела), база
делает `coalesce(p_count, e.count)`, `before = after`, и гейт триггера строку не пишет.

**Отказные ветки.** Пустая локация отсекается до запроса и названа поимённо, потому что
колонка `NOT NULL` и безымянный отказ RPC ничего бы не объяснил. Конфликт версий — своё
сообщение. Любая другая ошибка → «Не удалось сохранить изменения. Данные не изменены.»
**Отказ по роли неотличим от обрыва сети:** роль клиенту недоступна, поэтому кнопка
«Редактировать» показана всем, и пользователь без роли узнаёт об отказе на сохранении.

## 5. Создание оборудования

`/equipment/new`: способ учёта (`serialized` / `quantity`), поля, живой предпросмотр
карточки. Выбор `serialized` жёстко ставит `count = 1` и делает серийный номер
обязательным; варианта статуса `issued` в форме нет намеренно.

**Дефолт локации — константа, а не перевод.** `DEFAULT_LOCATION = 'Офис'`. Раньше
значение бралось через `tr()`, и при узбекском интерфейсе в базу уезжало `'Ofis'`, заводя
вторую локацию рядом с `'Офис'`, под которым лежит весь каталог. **Локация — данные, а не
текст интерфейса:** в базе один словарь значений на всех.

**Как хранится «без серийного номера».** В колонку `serialnumber` кладётся
`QTY::CODE::<код>` либо `QTY::AUTO::<uuid>` — это и есть «настоящее» хранение
`inventory_code`. `lengthinmeters` при пустом значении становится строкой `'N/A'`.

**«Добавить ещё» не перезагружает страницу.** Было `window.location.reload()`, стал
`resetForm()`. Мотив прикладной: партию заводят позициями подряд, и полный перезапуск SPA
на каждой при плохой сети рискует не подняться обратно.

### 5.1. Уникальность серийного номера — половина дыры закрыта

**ОСТАЛОСЬ: check-then-insert без ограничения в базе.** `serialNumberExists` делает
`head`-запрос с `.ilike`; `UNIQUE` на `equipment.serialnumber` в проде **нет** — есть
только обычный btree. Две вкладки, сохранившие один номер одновременно, обе пройдут
проверку. Нарушение правила 1 CLAUDE.md, лечится только ограничением в базе.

**ЗАКРЫТО: ошибка проверки больше не читается как «дубля нет».** Раньше `catch` возвращал
`false` — то же значение, что и успешная проверка чистого номера, то есть любой сбой
**разрешал** вставку. Теперь у проверки четыре состояния (`idle` / `unique` / `duplicate`
/ `failed`), и `'failed'` **останавливает сохранение**: «Не удалось проверить серийный
номер на дубли. Запись не сохранена». Разрешает только база — а раз уникального индекса
нет, «мы не знаем» не имеет права означать «можно».

Кнопку при `'failed'` намеренно **не** блокируют: отправка перепроверит номер сама.
Иначе один сетевой сбой запирал бы форму до перезагрузки.

**Экранирование шаблона.** В `ILIKE` символы `%` и `_` — подстановочные. Без обработки
серийник `AB_1234` совпадал с `AB-1234` и давал **ложный дубль**. Обратная косая
экранируется первой, иначе она экранировала бы уже добавленные косые.

Чего эта дыра **не** делает вопреки естественному предположению: `.ilike`
регистронезависима, поэтому «SN-001» при существующем «sn-001» она поймает; вставка идёт
через `.trim()`. Регистр и пробелы расхождения не дают — осталась ровно гонка.

**Справочник категорий** читает `select('type,subtype').range(0, 1999)`, кэш 24 часа.
**`.order()` в запросе нет ни одного** — при обрезке выборки в неё попадает произвольное
подмножество, а не «первые N». Верхняя граница — не 2000, а серверный `db-max-rows`.

## 6. Редактор списка

`/lists/new` или `/lists/:listId/edit`. Липкая шапка: «←», строка состояния на месте
eyebrow (без сдвига раскладки), h1 = имя списка, тройка действий «Сохранить · Рабочий
Excel · С реквизитами». Ниже — свёрнутая полоса реквизитов «имя · дата · заказчик ·
площадка»; после отказа экспорта «С реквизитами» незаполненное краснеет и кнопка меняет
подпись на «Заполнить», так что требование видно и на свёрнутой полосе.

**Высота сетки — замер, а не константа** (`useEditorChrome.ts`): хук складывает
`offsetTop` сетки по цепочке `offsetParent` с нижним отступом `.app-content` и пишет
результат инлайном, пересчитывая по `ResizeObserver` и `MutationObserver`. Константа
врала при баннерах («Черновик восстановлен», «Список не открыт») и при раскрытых
реквизитах; 244 px в CSS — запасное значение на один кадр до замера.

На ≤700 столбцы становятся вкладками, действия уходят в футер панели, **реквизиты стоят
ПОД панелями** (первый экран отдан оборудованию; порядок задаёт `order` на flex-контейнере,
JSX общий с десктопом — цена в том, что DOM-порядок для скринридера остался прежним).
Переключение вкладок помнит прокрутку каждой панели.

Страница распилена на шесть файлов: `ListEditorPage.tsx` (состояние выборки и
сохранение), `ListEditorMeta.tsx`, `useEditorChrome.ts`, `ListEditorCatalog.tsx`,
`catalogGroups.ts`, `useListDraftAutosave.ts`. **Сама страница — 811 строк, за порогом
распила.**

**Количество применяется на blur/Enter, а не посимвольно:** иначе «12» поверх «5»
проходило бы через `count = 1` и резало выбранные S/N. «Очистить список» и «Начать
заново» — двухшаговое подтверждение прямо в кнопке (`lib/useArmedAction.ts`).

### 6.1. Каталог редактора

Данные — `fetchAllEquipment()`: **весь** каталог одним кэшем `equipment:all`, TTL 10 минут,
страницами по 1000. Выход из цикла `if (batch.length < batchSize) break` **не различает**
«таблица кончилась» и «сервер обрезал страницу»: при `db-max-rows` меньше 1000 каталог
окажется усечён молча.

Эта выгрузка **не персистится** (`persist: false`): ~1.4 МБ JSON в `localStorage` съедали
треть квоты Safari. Цена — после перезагрузки редактор ждёт сеть вместо первого кадра.

Строки схлопываются в модели ключом `brand::model::type::subtype` в нижнем регистре
(`catalogGroups.ts`). Для группы считаются `totalCount`, `availableCount`,
`serializedItems`, `quantityAvailable`.

**Доступность определяется в браузере эвристикой по подстрокам:** недоступным считается
всё, что начинается на `«не »`, содержит `«диагност»` либо равно `issued`/`unavailable`.
Это разбор человекочитаемого текста, а не работа с перечислением. Русских статусов в
проде не осталось ни одного — русские ветки мёртвый код, и он **маскирует опечатку в
английском значении**: незнакомая строка молча считается недоступной.

Фильтры и поиск целиком клиентские и наружу не поднимаются. Селект подкатегории виден
сразу, без выбранной категории предлагая подтипы всего каталога. Показываются первые 60
групп, «Показать ещё» добавляет 60; смена фильтра сбрасывает лимит.

**Drawer рисует страница, а не панель:** у `.data-panel` и `.editor-grid` есть анимация с
`fill-mode: both`, и её `transform` стал бы блоком-контейнером для `position: fixed` —
drawer уехал бы внутрь панели.

### 6.2. Автосейв черновика нового списка

Собранный, но не сохранённый список переживает закрытие вкладки.

| Свойство | Значение |
|---|---|
| Когда пишется | только в режиме создания; у открытого списка источник правды — строка в базе |
| Пауза | 1 с после последнего изменения |
| Ключ | `list-draft:new` — **намеренно вне префикса `equipment-lists:`** |
| Срок жизни | 24 часа |
| Пустой черновик | не пишется и **стирает** уже записанный |

- **Ключ вне `equipment-lists:` — требование, а не небрежность.** Этот префикс целиком
  сбрасывается на каждом создании, правке и удалении — и унёс бы с собой работу, которую
  пользователь ещё не сохранял.
- **«Пустым» считается черновик без позиций, без описания и с пустыми названием,
  заказчиком и площадкой.** Иначе один заход на `/lists/new` без единого действия
  подсовывал бы плашку «черновик восстановлен».

**Восстановление** читается один раз, в начальном стейте, и только когда нет `listId`.
Выборка восстанавливается позже и **только по живому каталогу**: пока каталог грузится,
восстановление не запускается — «ничего не нашлось» стёрло бы черновик вместо того,
чтобы его вернуть. Автосейв заблокирован флагом, пока восстановление не закончилось:
стартовый пустой стейт затёр бы сохранённое раньше, чем оно успеет подняться.

Плашка «Черновик восстановлен» называет, ЧТО восстановлено: «единиц: N · изменён
21.08, 18:40». Без этих двух чисел «восстановлен» относилось непонятно к чему: состав
лежит на другой вкладке, и решение нажать необратимое «Начать заново» принималось вслепую.
Если часть позиций не нашлась — там же «позиций больше нет в каталоге: N».

### 6.3. Два режима: `specific` против абстрактного

Режим **не выбирается пользователем**, а выводится при сохранении: `specific`, если ни
одна позиция не осталась `planned`. Хранится в `equipment_lists.list_mode`.

**Выборка хранит КЛЮЧ группы, а не снимок группы.** Элемент выборки —
`{ key, label, count, serialIds, serialPickerOpen }`, где `label` — минимальный снимок
подписи, нужный ровно в одном случае: группы больше нет в свежем каталоге и строку нечем
нарисовать. Сам объект группы берётся из актуальной `Map` на рендере. Раньше в выборке
лежала копия группы на момент клика, и обновление склада до панели **не доезжало**.

Позиция, для которой группы больше нет, **не выбрасывается**: рисуется по снимку подписи
с пометкой «нет в каталоге» и предупреждением, что уйдёт в документ как планируемая.

**Как `buildItems` раскладывает выбор на позиции:**

1. **Отмеченные серийные номера** → по позиции на каждый, `serialized`, `count: 1`,
   реальный `equipment_id`. Единицы берутся только из **живой** группы.
2. **Остаток** разбирается по количественным единицам: `min(остаток, item.count)` на
   каждую, `quantity`, реальный `equipment_id`.
3. **Что не покрылось складом** — одна позиция `planned` **без `equipment_id`**. Сюда же
   целиком уходит позиция, чьей группы в каталоге не осталось.

Отсюда и режим: появился хоть один `planned` — весь список становится `abstract`. Просто
взять модель, не отмечая серийники, — нормальный сценарий: пункты 2 и 3 покроют его сами.

**Расчёт остатков целиком в браузере, по кэшу до 10 минут.** Сервер при сохранении наличие
**не проверяет** (§11, строка «в»). Пользователь может десять минут собирать список по
остаткам, которых уже нет.

### 6.4. Открытие сохранённого списка

**Гидратация разведена на две.** Шапка документа заполняется, как только приехала строка
списка, и каталог не ждёт; состав восстанавливается отдельно, когда приехал каталог.
Раньше и то и другое шло одним эффектом, и на холодном старте приехавшие данные затирали
название, которое пользователь успел набрать за эти секунды.

**Восстановление выбора молча отбрасывает позиции, для которых группа не нашлась.**
Практический эффект: если единицу удалили или переименовали её бренд/модель, при открытии
строка исчезнет без предупреждения, а следующее сохранение запишет усечённый состав.
**Асимметрия:** у черновика такая потеря показывается плашкой «позиций больше нет в
каталоге: N», у сохранённого списка — нет. Это разные пути кода, и второй остался
молчаливым.

`reservation_start` и `reservation_end` заполняются **одной и той же** датой — окно
всегда однодневное, второго поля в интерфейсе нет.

**Несохранённые правки предупреждают при закрытии вкладки.** Снимок документа берётся при
гидратации и обновляется после сохранения; пока текущее состояние расходится, на `window`
висит `beforeunload`. Только для `/lists/:id/edit` — у `/lists/new` работает автосейв.
Внутренняя навигация **не перехватывается**: роутер — `BrowserRouter` без data router,
`useBlocker` недоступен.

## 7. Сохранение списка

Excel можно скачать и **не сохраняя** — это разные кнопки и разные пути (§10).

**Реквизиты без дефолтов.** «Проект», «Заказчик», «Площадка» стартуют пустыми
(плейсхолдеры — подсказки, не значения). Пустое имя при сохранении → автоимя «Список
21.08.2026 · 14:32»; в поле оно не подставляется, но после записи поле и h1 получают то
имя, что ушло в базу.

| Решение | Кто |
|---|---|
| Членство в приложении, непустое имя, допустимость `list_mode` | БАЗА |
| Парность и порядок дат, непустой список позиций | БАЗА |
| **Существование `equipment_id`** у `serialized`/`quantity` | БАЗА |
| **Соответствие brand/model этому `equipment_id`** | **никто** — вставка дословно из JSON |
| **Хватает ли запрошенного на складе** | **никто** |
| Кто владелец записи | БАЗА, `auth.uid()` |

**Состав хранится ОДНОЙ копией** (с10): строка `public.equipment_lists` с `equipment_ids`
(массив uuid только серийных позиций) и `equipment_items` (jsonb всех остальных). Вторая,
нормализованная форма `equipment_reservation_items` снесена вместе с жизненным циклом.

**Правка — это replace, а не merge:** RPC блокирует строку `for update` и переписывает
её целиком.

**Куда попадает пользователь после первого сохранения.** Ветка `create`/`update`
выбирается по `listId` из URL, а у `/lists/new` параметра нет. Поэтому сразу после
создания редактор переходит на `/lists/<id>/edit` через `navigate(…, { replace: true })`:
адрес становится единственным источником правды, и все следующие «Сохранить» идут в
`update_equipment_list_document`. Тем же шагом стирается черновик.

**Повторное нажатие «Сохранить» обновляет ту же запись** — второй список не создаётся,
отдельного клиентского гварда идемпотентности для этого не нужно.

**Дыра целостности.** RPC вставляет `btrim(item->>'brand')`. Если ключ **отсутствует** —
будет `NULL` и падение по `not null`. Но если ключ есть и пуст, `btrim('')` даёт `''`,
`NOT NULL` проходит, и в таблицу ложится **пустая строка**.

## 8. Реестр `/lists`

Поиск, период и страницы считает база.

| Что | Кто |
|---|---|
| Окно страницы и общее число | БАЗА, `.range()` + `count: 'exact'` |
| Поиск | БАЗА, `.or(...)` с `.ilike` по `name`, `client_name`, `venue` |
| Фильтр периода | БАЗА, `.gte`/`.lte` по `reservation_start` |
| Порядок | БАЗА, `created_at desc, id desc` |
| Дебаунс ввода и зажим номера страницы | КЛИЕНТ |

- **Сортировка двухключевая.** `created_at` не уникален — импорт кладёт пачку одной
  секундой, — и без второго ключа строка могла попасть на две соседние страницы сразу
  либо не попасть ни на одну.
- **Период меряется по дате НАЧАЛА мероприятия.** Список без даты в любой период не
  попадает: сравнение с NULL ложно, и это честнее, чем показывать «этот месяц»
  вперемешку с недатированными.
- **Размер страницы — 12 на десктопе и 6 на мобильном**, число отдаёт сама фича: оно
  входит в ключ кэша, и прогрев спрашивает у неё же.
- **Строка поиска тримится до запроса** — иначе пробел в поле включал бы подпись
  «Найдено списков».
- **51-й список раньше был недостижим из интерфейса**: реестр брал `.limit(50)` без окна,
  а поиск работал по этим пятидесяти строкам в браузере.

**Несохранённый черновик виден первой карточкой** (с11): `ListsPage` читает его
напрямую из `localStorage` — запроса не нужно — и рисует с бейджем «Не сохранён», числом
единиц, временем правки и парой «Продолжить» / «Отбросить». Карточка **скрыта под
поиском, фильтром периода и вне первой страницы**: черновика нет в базе, а счётчик
«Найдено» считает только серверную выборку — карточка в фильтрованной выдаче означала бы,
что счётчик врёт. По той же причине она не участвует в пагинации.

**Счётчик меняет смысл вместе с фильтрами:** без них «Всего: N», с ними «Найдено: N».
Число одно и то же — `total` текущей выборки; второй ходки за общим числом нет намеренно.

**Пустых состояний два, и путать их нельзя:** `total === 0` без фильтров —
иллюстрированная заглушка «Сохранённых списков пока нет» с кнопкой создания; ничего не
нашлось под фильтр — сухое «Списки не найдены». Рисовать «пока ничего нет» человеку,
который просто опечатался в поиске, — враньё.

**Расхождение «12 единиц» над 11 строками объяснено.** Счётчик в шапке состава считает по
`equipment_ids`, а сам состав — по строкам, которые реально пришли со склада. Если
серийную единицу удалили, её id остался, а строки нет. Сборщик возвращает вторым полем
`missingUnits`, и drawer показывает «N единиц из состава не найдены на складе».

**Легаси-фолбэк схемы обезврежен.** До с5 `fetchEquipmentLists` при **любой** ошибке
первого запроса уходил в легаси-ветку: сетевой сбой или 401 давал вымышленные данные,
и они ложились в кэш на 10 минут. Теперь `withLegacySchemaFallback` пускает второй заход
только на `PGRST205`/`42P01`/`PGRST204`/`42703` — настоящее отсутствие таблицы или
колонки. Сетевой сбой, 401 и отказ RLS летят наружу как есть. Сама ветка жива, но
недостижима без реальной поломки схемы.

## 9. Удаление списков

Кнопка показана **для любого списка любому вошедшему**: ни статус, ни владелец, ни роль
в условии отрисовки не участвуют — роль клиенту недоступна.

Решает целиком база. **Тонкость механики:** RLS не возвращает ошибку — она просто не даёт
строке попасть под `delete`, и запрос завершается успешно с нулём строк. Поэтому отказ
распознаётся по отсутствию данных: `deleteEquipmentList` бросает `LIST_DELETE_FORBIDDEN`,
и drawer показывает «Удалять списки может только администратор склада».

**Действует политика `equipment_lists_delete_for_default_account`** — удалять может
только `auth.jwt() ->> 'email' = 'argo@argomedia.uz'`. Роль `admin` права удаления
**не даёт**: её политику снесли миграцией. Привязка к почте вместо роли — долг, строка
в `current-state`.

Каскад: `equipment_movements` — `on delete set null`, движения переживают удаление,
теряя ссылку на список.

## 10. Экспорт в Excel

Две кнопки в двух местах — в редакторе и на карточке сохранённого списка: «Рабочий Excel»
и «С реквизитами». Формат в списке не хранится, он выбирается в момент скачивания.
**«С реквизитами» требует названия, заказчика и площадки** — иначе подсветка полей,
красная строка состояния и прокрутка к панели. Это UX, а не защита: документ собирается
в браузере, пары в базе у такой проверки быть не может.

**База не участвует вообще** — файл собирается в браузере и никуда не отправляется. БАЗА
нужна лишь как источник строк для сохранённого списка.

`features/lists/xlsxExport.ts`, **без единой внешней библиотеки** — в зависимостях проекта
только `@supabase/supabase-js`, `lucide-react`, `react`, `react-dom`, `react-router-dom`.

| Слой | Реализация |
|---|---|
| OOXML | восемь частей пакета собираются конкатенацией строк |
| CRC32 | ручная побитовая реализация, полином `0xedb88320` |
| ZIP | самописный, **метод store (без сжатия)**; флаг `0x0800` — имена в UTF-8 |
| Отдача | `Blob` → `createObjectURL` → `<a download>` → `revokeObjectURL` через 1000 мс |
| Имя файла | `ДАТА_Имя_рабочий.xlsx` / `…_на-согласование.xlsx` (uz: `ishchi` / `kelishuvga`); `\ / : * ? " < > \|` заменяются на `-` |
| Реквизиты юрлица | `documentDefaults.ts` — единственное место |
| Пустые реквизиты | **в документ не выводятся**; сетка листа переменная — `getSheetMetrics(input, metadataRows)` |

**Экранирование XML есть** — функция `xml()` экранирует пять символов и вызывается во всех
местах, куда попадает пользовательский текст. Единственная неэкранированная подстановка —
`sheetName`, но это вычисленная константа. Название списка с амперсандом битого файла
не даёт.

**Область печати считается той же функцией от того же `buildMetadata`,** что и сетка
листа, — две сборки разойтись не могут.

**Два независимых сборщика состава для одного и того же списка.** Из редактора строки
берутся из склейки выборки с живым каталогом; из карточки состав собирается заново
(`loadSavedListComposition`: `fetchEquipmentByIds` по `equipment_ids` плюс
`equipment_items`). **Совпадение результатов ничем не гарантировано.**

**Группировка состава — по нормализованной паре бренда и модели.** Раньше ключом была
тройка из сырого текста, и в `jsonb` количественных позиций лежит **снимок** бренда на
момент сохранения, тогда как серийная часть читает подпись из живой `equipment`. После
переименования модели два источника расходились, и **одна позиция показывалась двумя
строками**. Теперь подпись берётся по `equipment_id` как более авторитетному, снимок —
фолбэк для позиций без id.

**Отказная ветка, о которой стоит знать:** если состав уже в кэше и не просрочен, экспорт
сохранённого списка **пройдёт при лежащей сети** — на данных до 10 минут давности.

## 11. Где клиент решает за базу — сводка

Правило проекта (CLAUDE.md, п. 2): клиентская проверка права или уникальности без пары в
базе — дыра.

| Что проверяет клиент | Что должно быть в базе | Статус |
|---|---|---|
| **(а)** Уникальность серийного номера — check-then-insert | `UNIQUE` на `equipment.serialnumber`; **в проде отсутствует** | **ДЫРА.** Две одновременные вкладки создают дубль. Регистр, пробелы и `_`/`%` расхождения не дают — осталась ровно гонка |
| **(б)** Клиент шлёт `brand/model/type/subtype` позиции; сервер их не сверяет с оборудованием | Сверка текста со строкой `equipment`, на которую указывает `equipment_id` | **ДЫРА.** Существование `equipment_id` проверяется, соответствие текста — нет |
| **(в)** `requested_count` со складом не сверяется при сохранении | Проверка наличия в RPC либо явное решение «список может быть сверхлимитным» | **ОТКРЫТО.** В базе может лежать список на 9999 единиц. Клиентское «больше текущего остатка» — только текст |
| **(г)** Расчёт остатков — целиком в браузере, по кэшу до 10 минут | Серверный расчёт доступности на момент сохранения | **СУЖЕНО, не закрыто.** Свежие остатки доезжают до панели, но между приходом каталога и сохранением склад может измениться |
| **(д)** `tracking_mode` и `inventory_code` — **не колонки БД**, а разбор строки `serialnumber` | Настоящие колонки либо один общий парсер | **ОТКРЫТО.** Второй, независимый парсер той же строки живёт в SQL-бэкфилле. Разойдутся — классификация в UI и в базе перестанет совпадать |
| **(е)** Клиент не прячет кнопки по роли — потому что **не может** | Требований нет: отзыв прав тут защита, а не недоделка | **Дыры нет.** Эффект только UX: кнопки видны всем, отказ приходит на сохранении. **Не «чинить» revoke** — см. `01-product` §2 |
| **(ж)** Право удалить список | — | **Дыры нет по безопасности.** Отказ распознаётся косвенно, по нулю возвращённых строк |
| **(з)** Версия карточки оборудования при сохранении | **ЕСТЬ в базе** — сверка `updated_at` внутри RPC | **Пара на месте.** Клиент только присылает версию и переводит `40001` в человеческий текст; отменяет правку сервер |

## 12. Сквозное поведение интерфейса

**Esc закрывает по одному слою за раз.** Раньше один Escape над открытым селектом внутри
drawer'а закрывал **и попап, и весь drawer вместе с несохранёнными правками**. Теперь
попап ловит Escape в фазе перехвата и гасит распространение (`usePopoverLayer.ts`), а слой
drawer'а слушает в фазе всплытия, то есть последним (`useModalLayer.ts`). Разбор —
`04-architecture` §11.

**Смена языка не делает ни одного сетевого запроса.** Функция `tr` меняется вместе с
языком и попадает в зависимости любого эффекта, где текст ошибки лежит в стейте строкой —
нажатие «UZ» перезапрашивало каталог, списки и состав. Теперь в стейте лежит **код или
флаг**, а текст собирается на рендере. Это не стиль, а защита от сетевого залпа на клик
по переключателю.

**Номер страницы зажимается на рендере** — и в каталоге, и в реестре.

### 12.1. Что человек видит, когда что-то ломается

**Экран «Что-то сломалось» вместо белого листа.** Необработанное исключение внутри
страницы ловит граница раздела: сайдбар и навигация остаются, в области контента —
красный блок с кнопкой «Перезагрузить». Экран гаснет сам, если человек ушёл в другой
раздел. Кнопка именно **перезагружает**, а не «пробует снова»: `React.lazy` запоминает
отказ загрузки кода, и повторная отрисовка того же места упала бы точно так же.

Корневая граница включается, только когда сломались общие части (сессия, язык, роутер).
**Разница видна сразу: есть сайдбар — сломался раздел, нет сайдбара — сломалось
приложение.**

**После выкатки вкладка чинит себя сама — один раз.** Вкладка со вчера, за ночь выкатили
новую версию, файлы старой исчезли. Клик по разделу → страница один раз перезагружается →
раздел открывается на новой версии. Ограничения, каждое со своей причиной:

- **Не чаще одного раза в минуту.** Если перезагрузка не помогла, вторая тоже не поможет,
  а вкладка ушла бы в мигающий цикл.
- **Никогда без сети.** Офлайн провал означает не «вышла новая версия», а «сети нет»;
  перезагрузка выбросила бы человека на браузерное «нет интернета» и унесла бы весь
  прогретый кэш.
- **Не срабатывает от фоновых загрузок.** Иначе вкладка могла бы уехать под человеком
  посреди заполнения формы. Перезагрузка привязана только к моменту, когда человек САМ
  нажал на раздел.

**Данные из кэша называют свой возраст.** «Обновлено 40 минут назад» и кнопка «Обновить».
Формы числительных даёт `Intl`, а не наша таблица. Бейдж **условный, и его отсутствие —
норма**: при живой сети он не появляется вовсе. Рядом с блоком «Ошибка загрузки» он скрыт —
два сообщения об одной беде противоречили бы друг другу.

**Чего эти механики НЕ делают.** Признака «вы офлайн» нет — есть только возраст данных.
Отказ никуда не отправляется: он оставляет строку в консоли (`[argo] …`). Сборщика ошибок
в проекте нет, шов под него готов (`04-architecture` §5).
