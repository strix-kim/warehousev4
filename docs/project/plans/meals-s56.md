## 1. Схема

Две таблицы, а не одна: у приёма пищи есть свои факты (статус, ссылка на расход), которые на строке заказа
повторялись бы N раз и расходились. Миграций две: **М1** — таблицы и ввод; **М2** — всё про расходы (колонка,
CHECK, замок, RPC). Если прораб снимет «В расходы» (развилка 7), М2 просто не пишется.

### 1.1 `public.project_meals` — приём пищи (день × слот), М1

| Колонка | Тип и ограничение |
|---|---|
| `id` | uuid pk default `gen_random_uuid()` |
| `project_id` | uuid not null → `projects` **on delete cascade** |
| `meal_on` | date not null (без default: `current_date` в базе — UTC, грабля `expenses`) |
| `slot` | text not null default `'lunch'`, `project_meals_slot_check`: `in ('lunch','dinner')` |
| `status` | text not null default `'collecting'`, `project_meals_status_check`: `in ('collecting','ordered','delivered')` |
| `created_by` | uuid default `auth.uid()` → `auth.users(id)` |
| `created_at`, `updated_at` | timestamptz not null default `now()` |

- UNIQUE `project_meals_slot_key (project_id, meal_on, slot)` — пара к «одна карточка обеда на день»; ведущий
  столбец обслуживает выборку по мероприятию, отдельный индекс не нужен.
- Текст с CHECK, не enum — канон проекта (`department`, `list_mode`).
- Триггер `guard_project_meal_day()` (before insert or update of `meal_on`, invoker, `search_path = ''`): у
  мероприятия есть `date_from`, и `meal_on` в `[date_from, coalesce(date_to, date_from)]`; иначе
  `raise exception 'project_meal_outside_period'`. Пара к выбору дня в UI. Сдвиг дат мероприятия потом старые
  обеды не трогает (UI показывает их отдельным днём «вне периода»).
- `update_project_meals_updated_at` на существующей `update_updated_at_column()`.
- `touch_project` не вешаем: реестр мероприятий обедов не показывает, лишний UPDATE `projects` на каждое блюдо.
- Строка создаётся лениво — при первом заказе дня/слота или смене статуса (раздел 3, `ensureMeal`).

### 1.2 `public.project_meal_orders` — строка «кто что», М1

**Одна строка на человека в приёме**, не на блюдо. «Плов + самса» пишется одной строкой — кафе так и читает;
сводка схлопывает одинаковые строки. Строка-на-блюдо требовала бы третью сущность «едок» ради отметки «не ест».

| Колонка | Тип и ограничение |
|---|---|
| `id` | uuid pk |
| `meal_id` | uuid not null → `project_meals` **on delete cascade** |
| `employee_id` | uuid null → `employees` **on delete restrict** |
| `guest_name` | text null — человек вне состава / «Общее» (водитель, гость, лепёшки на всех) |
| `dish` | text null; **null = «не ест / своё»**; строки нет вовсе = «ещё не спросили» |
| `qty` | smallint not null default 1, `project_meal_orders_qty_check`: `1..99` |
| `price` | bigint null — цена **за порцию**, `project_meal_orders_price_check`: null или `1..10 000 000` |
| `created_by`, `created_at`, `updated_at` | как у `project_staff` + `updated_at` |

- `project_meal_orders_person_check`: `(employee_id is null) <> (guest_name is null)` — ровно одно из двух.
- `project_meal_orders_dish_check`: `dish is null and price is null` либо `btrim(dish) <> ''` и длина ≤ 120.
  Отказавшийся без цены — иначе итог посчитает деньги за «не ест».
- `project_meal_orders_guest_check`: null либо непустое ≤ 80.
- UNIQUE `project_meal_orders_employee_key (meal_id, employee_id)` — **полное**, не частичное: NULL-ы гостей
  различны и не сталкиваются, а полное ограничение годится для `upsert(onConflict: 'meal_id,employee_id')`
  (частичный индекс PostgREST по `on_conflict` не выводит [предп.]). Пара к «одна строка на человека».
- UNIQUE-индекс `project_meal_orders_guest_key (meal_id, lower(guest_name)) where guest_name is not null` — защита
  от двойного нажатия «+ Гость».
- Индекс `(employee_id) where employee_id is not null` — под проверку FK `restrict`.
- **Почему `employee_id`, а не `project_staff.id`:** человека убрали из состава после обеда — его заказ и деньги
  остаются (каскад от `project_staff` стёр бы историю и разошёлся с расходом). UI показывает такого «вне состава».
- **Почему `restrict`, а не `cascade`/`set null`:** `set null` нарушил бы `person_check` (ошибка вместо обнуления),
  `cascade` молча стёр бы строку внесённого в расходы обеда. Удаление сотрудника — админская операция в SQL;
  `restrict` честно скажет «у него есть заказы».
- Триггер `normalize_meal_order_fields()` (invoker, `search_path = ''`): `dish := nullif(regexp_replace(btrim(dish),
  '\s+', ' ', 'g'), '')`, то же для `guest_name`. Схлопывание пробелов — чтобы «Плов» и «Плов  » в сводке были
  одним блюдом. Регистр не трогаем (показываем как ввели), группировку по `lower()` делает сводка.
- `update_..._updated_at` на `update_updated_at_column()`.

### 1.3 RLS и гранты (М1), образец — `project_staff` в `20261007184926_create_projects.sql`

Обе таблицы: select — `private.is_app_member()`; insert — `has_any_role(['technician','manager','admin'])` и
`created_by = auth.uid()`; update (using + with check) и delete — те же три роли. `revoke all … from public, anon,
authenticated` → `grant select, insert, update, delete … to authenticated`. Триггерные функции — `revoke execute
… from public, anon, authenticated` (gotchas §3). Изоляции между сотрудниками нет по замыслу.

### 1.4 RPC подсказок (М1)

`project_meal_dishes(p_project_id uuid) → jsonb [{dish, count}]`, `stable`, invoker, `search_path = ''`, проверка
`is_app_member`; группировка `lower(dish)` по всем приёмам мероприятия, порядок — по частоте. Скаляр под обрезку
1000 строк не попадает; счётчик для порядка чипов считает база. `revoke … from public, anon` + `grant execute …
to authenticated`, `notify pgrst`.

### 1.5 Расходы (М2)

- `project_meals.expense_id uuid null → expenses(id) on delete set null` + частичный индекс `where expense_id is
  not null` (под действие FK при удалении расхода).
- `project_meals_expense_status_check`: `expense_id is null or status = 'delivered'` — внесённый в расходы обед
  нельзя вернуть в «собираем».
- Замок `guard_meal_orders_locked()` (before insert/update/delete на `project_meal_orders`): родитель с
  `expense_id is not null` → `raise 'project_meal_locked'`. Пара к запертому в UI вводу: иначе сумма обеда и
  расхода расходятся молча. Разблокировка — удалить расход в журнале. Родителя нет (каскад удаления мероприятия)
  → пропускаем [предп.: проверить, что каскад проходит].
- `create_meal_expense(p_meal_id uuid, p_name text, p_amount bigint, p_spent_by uuid, p_comment text) → uuid`,
  **security invoker**, `search_path = ''`. Одна транзакция: `is_app_member` → `select … for update` обеда (нет —
  `meal_not_found`) → `status <> 'delivered'` → `meal_not_delivered` → `expense_id is not null` →
  `meal_expense_exists` → `insert into expenses (name, spent_on = meal_on из базы, amount, spent_by, comment)` —
  owner и роль проверит политика `expenses_insert_for_owner`, CHECK-и `expenses_*` → `update project_meals set
  expense_id`. Возвращает id расхода. Блокировка строки — пара к двойному нажатию и двум вкладкам.
- **Сумму шлёт клиент** (предзаполнена суммой цен, правится): у кафе бывает обслуживание 10–15 % и чек без цен по
  блюдам. Это не «вера клиенту»: сумма расхода — то, что человек вводит в свой же журнал, как в `ExpenseDrawer`.
  Что держит база — уникальность расхода на обед, статус, дата, владелец.

### 1.6 Что считает база и что клиент

| Что | Где | Почему |
|---|---|---|
| итог и «× N» на экране, текст сводки | клиент из строк приёма | строк ≤ ~60 на приём (состав + гости), обрезка 1000 недостижима; UX, не деньги |
| сумма, которая уходит в деньги | человек в дровере, запись — RPC | см. 1.5 |
| один расход на обед, дата расхода, статус | база (`for update`, CHECK, `meal_on`) | права и целостность |
| частота блюд для подсказок | база (`project_meal_dishes`) | выборка по всем дням может расти |

Клиентская страховка выборки строк приёма: `.order('created_at').order('id')` и отказ, если пришло ровно 1000.

### 3.2 UX для 390 (одна рука, на бегу)

- Вверху — горизонтальная лента дней-чипов периода (`date_to null` = один); по умолчанию — **сегодня**
  (`todayDateValue()`), если входит в период, иначе первый день. Дни с обедом вне периода — в конце ленты с пометкой.
  Мероприятие без дат → пустое состояние «Укажите даты мероприятия» со ссылкой на «Изменить».
- Слот «Обед / Ужин» — переключатель под лентой (развилка 1).
- Список: состав (`fetchProjectStaff`, порядок `sortStaff`) + строки вне состава + гости. Строка целиком — цель
  касания ≥ 48 px. Тап → лист заказа. «Сохранить → следующий» открывает следующего неспрошенного: гонец обходит
  бригаду без возврата к списку.
- Чипы подсказок: сначала блюда этого дня по частоте (из уже загруженных строк), потом мероприятия (RPC). Тап по
  чипу = блюдо введено, цена подставляется последней ценой этого блюда в мероприятии (подсказка, не правило).
- Цена: `inputMode="numeric"`, разрядка `groupDigits`; валюта `tr('сум','so‘m')`.
- Внизу прибита плашка: «Заказано 12 · не ест 2 · не спрошены 3 · 540 000 сум» + «Сводка».
- Запись — по «Сохранить» в листе, не по нажатию клавиш. Отказ — строка остаётся с пометкой «не сохранено,
  повторить» (мобильный интернет на площадке).
- Статус: одна кнопка «Дальше: Заказано» / «Дальше: Привезли»; шаг назад — в меню (`ActionMenu`). После
  «Привезли» кнопка «В расходы»; после внесения — «В расходах · 540 000 сум» (ссылка на `/expenses`, если расход
  читается этим аккаунтом, иначе «внесено другим аккаунтом») и ввод заперт.
- Сводка: «Для кафе» — только схлопнутые блюда и число порций; «Полная» — плюс «кто что» (раздать при приезде).
  «Поделиться» — `navigator.share({ text })` там, где он есть (на телефоне сразу открывает Telegram), иначе
  `copyText`. **Перед кодом сверить Web Share API по MDN** (не выдумывать API).
- Все тексты — `tr(ru, uz)`; текст сводки — на языке интерфейса.

### 3.3 Кэш

**Модуль ничего не кладёт в `persistentCache`.** Источник правды — база; экран читает её на каждом входе и после
каждой записи обновляет локальное состояние ответом записи. Почему: правят на бегу с телефона, кэш показал бы
несохранённое как сохранённое. Сбросы чужих кэшей: после `create_meal_expense` — экспортируемый сброс расходов
(шаг 0). `projects:` не трогаем — реестр обедов не показывает. Ключ «последний выбранный „Кто потратил“» —
`localStorage` в `try/catch` как удобство одного зрителя, допустимо, но не обязательно.

### 3.4 `database.types.ts`

Предпочтительно `generate_typescript_types` через MCP и перенос фрагментов двух таблиц и двух функций; если руками
— в `Insert` все nullable и колонки с default с `?`, в `Update` — все с `?` (грабля с54: `tsc` ловит сразу).
Правит ведущий сразу после каждой миграции, до запуска кодеров.

## 5. Риски

- **Миграции аддитивные**, старый бандл о новых таблицах не знает — выкатка М1/М2 прод не кладёт. Откат М1 —
  `drop` двух таблиц (прорабу в SQL Editor, MCP `drop` отклоняет).
- **RLS:** новые таблицы и запись в чужую owner-таблицу через RPC → `/rls-verify` обязателен. Отдельно проверить,
  что `create_meal_expense` под вторым аккаунтом пишет расход **в его** журнал, а не автору обеда.
- **Подмена ссылки прямым REST:** участник с ролью может `update project_meals set expense_id = null` и внести
  обед второй раз (вред — дубль в своём же журнале) или поставить чужой uuid. Лечится колоночным грантом без
  `expense_id` + `security definer` у RPC — развилка 6; рекомендую не лечить в MVP, строка в backlog.
- **Замок vs каскад:** удаление мероприятия с внесённым обедом каскадом удаляет строки заказов, замок не должен
  мешать [предп.]. Расход при этом остаётся — деньги не теряются, сводка живёт в его комментарии.
- **`restrict` на `employee_id`:** админ не удалит сотрудника, у которого есть заказы, без зачистки заказов.
- **Комментарий расхода ≤ 500** (`expenses_comment_check`): полная сводка на 30 человек длиннее → в комментарий
  идёт только «Для кафе», обрезка с «…» на клиенте.
- **Сдвиг дат мероприятия** оставляет обеды вне периода — показываются отдельно, не теряются.
- **Сеть на площадке:** отказ записи обязан быть виден на строке; без этого гонец уверен, что сохранил.
- **Лимит 1000:** строк приёма ≤ ~60; подсказки — RPC. Страховка на выборке строк (раздел 1.6).
- **Бандл:** новый ленивый чанк, библиотек не добавляется.
- **Тестов и линтера нет:** `mealSummary.ts` — расчёт, проверяется строго (scout: экран против SQL).
- **Расход виден только автору:** второй аккаунт видит «внесено другим аккаунтом» без суммы-ссылки.

## 6. Проверки

**Машиной (scout, строго — данные и права), REST с JWT `rls-test@argomedia.uz` + блоки с откатом:**
`anon` — 0 грантов на обе таблицы и обе функции; подмена `created_by` → 42501; не-staff (временная строка `users`
в откатываемой транзакции): insert/update/delete обеих таблиц и вызов `create_meal_expense` → отказ; чужие обеды
читаются вторым аккаунтом (общий доступ по замыслу); все именованные отказы раздела 2; два параллельных
`create_meal_expense` по одному обеду → успех один; расход второго аккаунта не виден первому, `expense_id` виден
обоим; удаление расхода → `expense_id` null; удаление мероприятия → обеды каскадом, расход цел; итог экрана =
`sum(qty*price)` = сумма расхода, когда сумму не правили.

**Глазами прораба (телефон 390 + одна десктопная ширина):** обход бригады «→ следующий» одной рукой; клавиатура
не закрывает поле цены и кнопку; чипы подсказок; текст в Telegram через «Поделиться»; степпер статуса; «В расходы»
и запертый ввод; оба языка; консоль чиста, горизонтальной прокрутки нет.

## 7. Развилки для прораба (рекомендация)

1. **Ужин в MVP:** колонка `slot` (`lunch`/`dinner`) сразу, переключатель «Обед / Ужин» в UI сразу — стоит
   один сегмент, монтажные ночи реальны. Альтернатива — колонка есть, UI только «Обед».
2. **Строка на человека, а не на блюдо** («Плов + самса» одной строкой). Почему: отметка «не ест» и upsert без
   третьей таблицы; кафе читает такую строку. Цена — `qty` у гостевых и «Общее».
3. **Люди вне состава:** гостевая строка с именем-текстом (водитель, гость, «Общее: лепёшки ×6») — да.
4. **Человека убрали из состава после заказа:** заказ остаётся, показан «вне состава» (привязка к `employee_id`).
5. **Сумма расхода — предзаполнена суммой цен и правится** (обслуживание, чек без цен по блюдам). Цены по
   блюдам необязательны. Альтернатива — сумма строго из базы, тогда цены обязательны у всех.
6. **Подмена `expense_id` прямым REST — не лечим в MVP** (вред — дубль в своём журнале), backlog. Альтернатива —
   `security definer` RPC + колоночный грант.
7. **«В расходы» в этой цели или следующей:** рекомендую в этой (шаг 6), но М2 отдельной миграцией — можно
   отложить без переделки шагов 1–5.
8. **Отдельный экран `/projects/:id/meals`**, на странице мероприятия — только ссылка. Альтернатива — блок на
   странице (тогда распил `ProjectPage` до кода).
9. **Ввод после «Заказано» не запираем** (люди передумывают); запираем только после «В расходы».
10. **Подсказки — только из этого мероприятия.** Между мероприятиями (одно кафе на площадке) — позже, одной RPC.
