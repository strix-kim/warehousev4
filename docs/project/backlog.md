## Дыры «клиенту не верим» (правило 2 CLAUDE.md)

Каждая — клиентская проверка без пары в базе. Порядок примерный по цене отказа.

- **Сервер не сверяет brand/model позиции с реальным оборудованием.** Миграция
  `20260819131611_edit_saved_equipment_lists.sql` вставляет `brand/model/type/subtype`
  дословно из клиентского JSON, проверяя только существование `equipment_id`.
  При этом `reservation_shortages` считает дефицит ДЖОЙНОМ склада по этому же
  денормализованному тексту. Расхождение в написании → `capacity = 0` и фантомная
  нехватка, либо склейка позиции с чужой группой. Лечится констрейнтом или триггером,
  который берёт brand/model ИЗ `equipment` по `equipment_id`, а не из запроса (с1).
- **Уникальность серийного номера держит только клиент, и держит плохо.**
  `serialNumberExists` (`.ilike`) вызывается перед `createEquipment` — classic
  check-then-insert, две вкладки пройдут проверку обе. `UNIQUE` на
  `equipment.serialnumber` в репозитории нет. **Но дыра шире гонки:** `checkSerial()`
  в `EquipmentCreatePage.tsx` обёрнут в `try/catch`, где `catch` возвращает `false` —
  любая ошибка запроса (сеть, 401, PostgREST) трактуется как «дубля нет», и вставка
  идёт. То есть уникальность отваливается при ЛЮБОМ сбое, а не только при
  одновременной работе двоих. Нужен регистронезависимый уникальный индекс — но
  **только после физической сверки наклеек**: аудит нашёл 11 повторяющихся
  нормализованных серийников, автоматически их чинить нельзя (с1, риск №1 AUDIT).
- **Количество не сверяется с остатком при сохранении списка.**
  `create_equipment_list_with_items` проверяет членство, имя, `list_mode`, парность дат,
  непустоту позиций и существование `equipment_id` — сверки `requested_count` с наличием
  НЕТ. Единственный физический гейт — переход `confirmed → issued`. До выдачи в базе
  может лежать бронь на 9999 единиц (с1).
- **Расчёт остатков и распределение по единицам — целиком в браузере**, по кэшу
  возрастом до 10 минут. `isAvailable` — эвристика по подстрокам («не », «диагност»,
  «в н») вместо явного статуса. Два пользователя одновременно соберут списки из одних
  и тех же единиц (с1).
- **`tracking_mode` / `inventory_code` — не колонки БД, а разбор строки `serialnumber`.**
  Парсер продублирован: один в TypeScript, второй в SQL-бэкфилле. Два независимых
  парсера одной строки разойдутся при первой правке одного из них (с1).

## Отказоустойчивость и диагностика

- **ErrorBoundary в проекте нет вообще.** Все шесть страниц грузятся через `React.lazy`,
  а `RouteBoundary` — это только `Suspense` без catch. Сценарий отказа реальный:
  выкатили новый билд → у пользователя с открытой вкладкой старые hashed-чанки исчезли →
  SPA-рерайт отдаёт HTML вместо JS → чанк не парсится → отклонённый промис в Suspense
  без границы → **белый экран всего приложения**. Лечится границей ошибок с предложением
  перезагрузить страницу (с1).
- **Ни одного `console.*` во всём `src/react`**, сборщика ошибок в зависимостях нет.
  Отказ у пользователя невидим: он не может ничего принести, кроме «не работает» (с1).
- **Офлайн не отслеживается.** В связке с кэшем, который при ошибке молча отдаёт старое
  значение, это даёт: сеть лежит → пользователь видит остатки и статусы прошлой недели
  без единого визуального признака. Нужен индикатор «данные из кэша от такого-то
  времени» (с1).
- **Legacy-фолбэк списков срабатывает на ЛЮБОЙ ошибке**, без фильтра по коду —
  в отличие от соседних функций, которые гейтятся по `PGRST202/42883/PGRST205/42P01`.
  Сетевой сбой или 401 на первом запросе → все списки получают `reservation_status:
  'draft'` и `advanced_features: false` → **выданный список показывается как «Сохранён»,
  цикл выдачи прячется** — и это кэшируется на 10 минут. Две копии кода, чинить обе (с1).
- **Молча проглатываемые ошибки:** загрузка справочника типов/подтипов гасится
  `.catch(() => undefined)` — подсказки просто пусты, сообщения нет; оба прогревочных
  таймера в `AppShell` — так же (с1).

## Схема и миграции

- **`equipment.serialnumber` объявлен `not null`, а TS-тип считает поле
  необязательным** (`src/react/features/equipment/types.ts:5`). Форма пропустит
  пустой серийник, а Postgres отобьёт вставку — ошибка вылезет не там, где её ждут.
  Привести тип к базе (с2).
- **`public.users.id` не связан внешним ключом с `auth.users`.** Вся авторизация
  держится на совпадении этих идентификаторов (`private.is_app_member()` сверяет
  `u.id = auth.uid()`), но база это совпадение не гарантирует: профиль с чужим `id`
  вставится молча, а его владелец никогда не пройдёт проверку членства. Соседние
  таблицы при этом ссылаются на `auth.users(id)` напрямую — в схеме две разные
  привязки к пользователю. Чинится FK после сверки существующих строк (с2).
- **Удаление списков захардкожено на почтовый адрес.** Политика
  `equipment_lists_delete_for_default_account` требует
  `auth.jwt()->>'email' = 'argo@argomedia.uz'`; роль `admin` права удаления не даёт
  вообще. Смена почты у владельца молча отберёт возможность удалять, и в интерфейсе
  это будет выглядеть поломкой приложения. Перевести право на роль (с2).
- **GIN-индекс полнотекстового поиска `idx_equipment_search` существует, но не
  используется:** каталог ищет через `ilike`, а не через `to_tsvector/@@`. Индекс
  только удорожает запись. Либо перевести поиск на него, либо удалить (с2).
- **Дубль внешнего ключа на `mount_points`:** `mount_points_event_id_fkey` и
  `mount_points_event_fk` — одна пара колонок, одно `on delete cascade`. Плюс четыре
  триггера пересчёта вместо одного (`trg_mount_points_count` уже покрывает
  insert/delete/update, а `mount_point_insert/update/delete` дублируют его поштучно).
  Порчи данных нет — функция пересчитывает счётчик заново, — но работа делается дважды.
  Таблица legacy, срочности нет (с2).
- **Мёртвый код: разбор русских статусов оборудования.** `isAvailable` в
  `ListEditorPage.tsx:82-86` понимает `'в н'`, `'диагност'`, `'не '`, хотя в проде на
  1481 строку остались только английские значения (`available` 1475, `unavailable` 5,
  `diagnostics` 1). Ветка не срабатывает и при этом маскирует опечатку в английском
  значении: незнакомая строка молча считается недоступной (с2).
- **Второго аккаунта для `/rls-verify` не существует.** В проде ровно один
  пользователь: `auth.users` — 1 строка, `public.users` — 1. Прогон под двумя
  аккаунтами, обязательный для всего, что касается прав, физически невозможен, пока
  второй аккаунт не заведён (с2).
- **`revoke all on public.users from authenticated` + `security definer`.** Авторизация
  цела ИМЕННО потому, что `private.is_app_member()` и `private.has_any_role()` объявлены
  `security definer`. Любая «починка» revoke без понимания этого уронит вход всем.
  Занесено в библию `03-data-model` как связанная пара — не разносить (с1).
- **Битая кодировка внутри SQL:** в `scripts/2026-08-19_reservations_history_rls.sql`
  строка про наличие содержит символ замены U+FFFD («В н␦личии»). Если по этой строке
  идёт сравнение статусов — сравнение не сработает. Проверить и починить (с1).
- **11 повторяющихся нормализованных серийных номеров** в каталоге. Автоматически не
  чинятся — нужна физическая сверка наклеек (риск №1 AUDIT, с1).
- **Пустые старые таблицы** оставлены для обратной совместимости и клиенту больше не
  доступны. После контрольного периода — удалить отдельной обратимой миграцией
  (риск №6 AUDIT, с1).

## Аудит архитектуры 2026-08-20 (с4)

Полный отчёт — `docs/project/audits/2026-08-20-architecture.md`. Семь аудиторов
по измерениям, каждая находка проверена отдельным скептиком по коду; 66 выжило,
5 отклонено. Ниже вынесено то, что требует решения раньше остального; остальные
находки живут в отчёте с якорями и сценариями отказа, дублировать их сюда не нужно.

- **HIGH: повторное «Сохранить» на `/lists/new` создаёт ВТОРОЙ список.**
  `persistList` (`ListEditorPage.tsx:377`) ветвится по `listId` из `useParams`, но
  маршрут `/lists/new` объявлен без параметра (`App.tsx:33`) — там `listId` пуст
  навсегда. Единственное место, где оседает id созданной записи, — `savedId` (`:378`),
  и он гасится при ЛЮБОЙ правке полей (девять мест) и состава (четыре). Сценарий
  бытовой: сохранил → поправил букву в названии → сохранил → в базе два списка;
  три правки дают четыре списка. Удаление прибито к одной почте
  (`equipment_lists_delete_for_default_account`), поэтому обычный сотрудник дубли
  не уберёт. **Найден независимо двумя измерениями, подтверждён обоими скептиками
  построчно.** Лечится `navigate('/lists/:id/edit', {replace:true})` после создания.
  Тем же коммитом обязательно править `02-features.md:499`, где сохранение названо
  «идемпотентным в пределах экрана» — доке верят, и это делает дефект дороже (с4).
- **Библия врёт в трёх местах, найдено аудитом:** `02-features.md:499`
  («идемпотентно» — ровно место HIGH), `06-design-system.md:153` (мёртвый
  `.mode-switch` перечислен как живая тач-зона), `04-architecture.md:175-177`
  (`immutable` «на этот сценарий не влияет» — опровергнуто живым curl по проду).
  Чинить при первом касании соответствующего кода (с4).
- **Порядок работ на шесть сессий предложен аудитом** и прорабом не утверждён:
  сначала выстрелившее (HIGH + локация + счётчики), затем типы базы, затем сведение
  контрактов, кэш, конфигурация, и только последними — распилы. Обоснование каждого
  шага — в отчёте, раздел «Порядок работ» (с4).
