# Грабли: операционный справочник

**Как пользоваться.** Файл целиком НЕ читай. Найди свою задачу в триггерной карте →
открой ТОЛЬКО указанный раздел → пройди его pre-flight чеклист. Это операционный
справочник, а не учебник.

**Как пополнять.** Раздел заводится, когда грабля РЕАЛЬНО случилась в сессии, и
пишется формулой «симптом → причина → правило». Гипотетические опасности сюда не
кладём: файл ценен тем, что каждая строка оплачена. Источник строки — либо
наблюдение в этом проекте (тогда ставим номер сессии), либо документированное
поведение движка/библиотеки (тогда помечаем «движковое»).

## §1 Data API (PostgREST через supabase-js)

**Pre-flight:**
- [ ] Выборка может вернуть больше 1000 строк? Тогда нужен явный батчинг/пагинация.
- [ ] Ожидаешь ровно одну строку — `.single()` или `.maybeSingle()`?
- [ ] Ошибку запроса реально проверяешь, а не только `data`?

| Симптом | Причина | Правило |
|---|---|---|
| Список «обрывается» на круглом числе, ошибок нет | у Data API есть предел числа строк в одном ответе (по умолчанию 1000) — лишнее просто не приходит, это не ошибка | большие таблицы читать порциями через `.range()`; предел не «примерно», а жёсткий (движковое) |
| Добавил `.order()` к выборке — и из справочника пропала целая категория | с явным порядком обрезка на 1000 становится РОВНОЙ: хвост сортировки отрезается целиком, а не случайными строками (с8, `fetchEquipmentTaxonomy`: 897 строк одной категории упёрлись в предел) | порядок — только вместе с батчами по 1000 и полным ключом сортировки (`…, id`), иначе страницы перекрываются |
| `.single()` роняет запрос там, где раньше работал | `.single()` требует РОВНО одну строку: ноль или две — уже ошибка | ждёшь «ноль или одна» — `.maybeSingle()`; ждёшь ровно одну — обрабатывай ошибку явно (движковое) |
| `data` пустой, приложение молчит | у supabase-js ошибка не бросается, а лежит в `error` рядом с `data` | проверять `error` в КАЖДОМ запросе; «нет данных» и «запрос упал» — разные состояния (движковое) |

|---|---|---|

| Клиент проверяет уникальность перед вставкой | две одновременные вкладки пройдут проверку обе | уникальность держит ограничение в базе; клиентская проверка остаётся только как подсказка |

## §3 Миграции и схема

**Pre-flight:**
- [ ] Изменение схемы оформлено файлом в `supabase/migrations/`?
- [ ] Код, который ждёт новой колонки, поедет ПОСЛЕ миграции, а не раньше?

| Симптом | Причина | Правило |
|---|---|---|
| В репозитории миграции есть, а в проде схема другая | схема живёт вне git; правки кликами в дашборде репозиторий не видит | любая правка схемы фиксируется миграцией в ту же сессию, даже если применена руками |
| Выкатили код — приложение упало на проде | код ждал колонку, миграция не применена | порядок: миграция → проверка → код. Обратный порядок кладёт прод |
| Непонятно, применён ли `scripts/*.sql` | это исторические ручные скрипты, не механизм миграций | новые SQL кладём только в `supabase/migrations/`; `scripts/` — архив без гарантий |
| Новая функция доступна `anon`, хотя миграция делала `revoke from public` | default privileges Supabase выдают EXECUTE на каждую новую/пересозданную функцию НАПРЯМУЮ `anon`/`authenticated` — revoke с `public` прямой грант не снимает | каждый `create [or replace] function` сопровождается явным `revoke ... from public, anon` + grant нужным ролям, а после применения — контрольная выборка `information_schema.routine_privileges` (с5, поймано дважды) |

## §4 Кэш

**Pre-flight:**
- [ ] Данные, которые ты меняешь, лежат в `persistentCache`? Кто сбрасывает?
- [ ] После записи пользователь увидит новое или старое?

| Симптом | Причина | Правило |
|---|---|---|
| После сохранения список показывает старое | у значения два хранилища — база и кэш — и запись обновила только одно | у каждого кэшируемого значения один владелец и явное правило сброса (правило 5 `CLAUDE.md`) |
| Второй аккаунт видит фантом удалённой записи | кэш пережил изменение прав/данных | при проверке прав сверяться с базой, а не с экраном |
| «Не обновилось» после выкатки | статика отдаётся с длинным immutable-кэшем (`vercel.json`) | сначала проверь, не смотришь ли в браузерный кэш; только потом ищи баг |
| Флаг «запрос отказал», выставленный в `.catch`, никогда не загорается | `cachedQuery` при ЖИВОЙ записи подменяет провал последним значением и промис резолвится — `.catch` вызывается только без кэша (с8, `DataAge failed`) | признак отказа — метка `touchedAt` до и после запроса: кэш двигает её только на успешном ответе; не сдвинулась — ответа с сервера не было |
| Сменил форму значения в кэше — первый кадр после выкатки читает старую | запись пережила выкатку в `localStorage` под тем же ключом (TTL до суток у справочников) | смена формы = смена ключа (`…:v2`); старые записи осиротеют и выпадут по TTL (с5 `composition:v2`, с8 `equipment-taxonomy:v2`) |

**Pre-flight:**
- [ ] Эффект переживёт двойной вызов в разработке?

| Симптом | Причина | Правило |
|---|---|---|

## §7 Роутинг и SPA

| Симптом | Причина | Правило |
|---|---|---|
| Любой несуществующий путь открывает приложение вместо 404 | в `vercel.json` стоит рерайт `/(.*) → /` — это норма для SPA | «страница открылась» не доказывает, что маршрут существует; 404 рисует само приложение |
| Прямая ссылка на чужую запись открывается | маршрут доступен всем, кто знает адрес | доступ решает база, а не наличие ссылки в интерфейсе (см. §2) |
| Дровер закрыли крестиком, шаг «назад» открывает его снова | открытие пушит запись с `?item=…`, а закрытие пушит или просто убирает параметр — «назад» ведёт обратно на запись С параметром | открытие — push, закрытие — `replace`: пушенная запись заменяется, и «назад» уходит туда, где дровера не было (с11) |
| Поле ввода теряет набранные буквы после дебаунса в адрес | синхронизация «адрес поменялся → обнови поле» не отличает СВОЮ запись от чужой, а своя прилетает через паузу, когда человек уже набрал следующие символы | помнить последнее записанное значение в ref и догонять адрес только при расхождении с ним (с11) |
| Первый кадр из кэша показывает не то, что просит адрес | прогрев читает ключ БЕЗ фильтров, а фильтры теперь приходят из query | прогревать только нетронутый экран; под фильтром честнее скелет, чем секунда чужой выдачи (с11) |

**Pre-flight:**
- [ ] `npx tsc -b` и `npm run build` зелёные?
- [ ] Не вырос ли бандл?

| Симптом | Причина | Правило |
|---|---|---|

Ветка отстала — `git merge --ff-only main`, ничего не потеряно (с11) |
| `tsc -b` «не видит» свежую ошибку | сборка инкрементальная и кэширует состояние | сомневаешься — `npx tsc -b --force` |

| Локально собралось, на Vercel упало | другая версия Node и другие переменные | `engines.node` = 22.x; расхождение среды — первая гипотеза, не последняя |
| `curl` по превью-деплою и bypass-ссылка из MCP уходят на логин vercel.com | у проекта включена Vercel Authentication на ВСЕ превью (`ssoProtection: prod_deployment_urls_and_all_previews`); сам прод-домен при этом открыт | защита оставлена осознанно (репозиторий публичный): агент проверяет превью по build- и runtime-логам, снаружи кликает прораб. Не считать это поломкой деплоя и не выключать защиту без прораба (с6) |
| `npm run preview` отдаёт на пропавший `/assets/*.js` `200 text/html`, а прод — 404 | у `vite preview` собственный SPA-фолбэк, рерайтов из `vercel.json` он не знает | обработка провала чанка срабатывает в обоих случаях (`import()` падает и на HTML вместо модуля), но САМ СТАТУС ответа проверять только на проде (с6) |
| Откатились на прошлый билд — у пользователей всё равно белый экран | байт-в-байт тот же билд даёт те же хэши чанков, а 404 по ним уже закэширован на год с `immutable` | откат делается ВПЕРЁД: новой сборкой с новыми хэшами. Заголовками это не лечится — Vercel не кондиционирует их по статусу ответа (с5→с6) |

## §11 Отказные ветки этого проекта

Раздел заведён по итогам разбора кода в с1. Каждая строка — реальный механизм в
`src/react`, а не гипотеза. Общая болезнь: **отказ здесь трактуется как «данных нет»,
а не как «мы не знаем».** Прежде чем писать новый `catch`, посмотри, во что он
превратит состояние экрана.

**Pre-flight:**
- [ ] Твой `catch` возвращает значение? Тогда это значение станет фактом для UI.
- [ ] Фолбэк на «старый способ» гейтится по КОДУ ошибки, а не по самому её наличию?
- [ ] После твоей правки ошибку видно пользователю или она исчезает молча?

| Симптом | Причина | Правило |
|---|---|---|
| Выданные списки показываются как «Сохранён», и это держится 10 минут | фолбэк на legacy-схему срабатывает на ЛЮБОЙ ошибке первого запроса, без фильтра по коду — сетевой сбой или 401 уводят в ветку «старая база», где статус жёстко проставляется черновиком; результат кладётся в кэш | фолбэк на другой способ ВСЕГДА гейтится по коду ошибки (`PGRST202`, `42883`, `PGRST205`, `42P01`), как это сделано в соседних функциях того же файла. Иначе сбой сети переписывает данные (с1) |
| Дубль серийного номера прошёл при живой проверке уникальности | проверка обёрнута в `try/catch`, где `catch` возвращает «дубля нет»: любая ошибка запроса читается как разрешение вставить | `catch` вокруг ПРОВЕРКИ не имеет права возвращать разрешающее значение. Неизвестно — значит блокируем и говорим об этом; разрешает только база (с1) |
| Подсказки типов и подтипов пусты, ошибки нет | загрузка справочника гасится `.catch(() => undefined)` | пустой результат и провал загрузки — разные состояния экрана. Гасить ошибку можно только там, где пользователю всё равно (с1) |
| Пользователь работает с данными недельной давности и не знает об этом | кэш при ошибке сети отдаёт старое значение, ошибка до UI не доходит; офлайн нигде не отслеживается | отдал старое — обязан сказать, что оно старое, и назвать возраст (с1) |
| После выкатки у пользователя с открытой вкладкой белый экран | страницы грузятся лениво, а чанков старого билда на проде уже нет | **закрыто в с6**: все шесть страниц идут через `lazyWithReload` (одна перезагрузка в минуту, офлайн — экран границы), сверху две границы ошибок. Правило осталось: новый ленивый маршрут заводится ТОЛЬКО через `lazyWithReload`, голый `lazy` в `App.tsx` — регресс (с1→с6) |
| Отказ у пользователя невозможно разобрать | сборщика ошибок в зависимостях нет | **частично закрыто в с6**: есть канал `lib/reportAppError.ts` — единственное место в `src/react`, где разрешён `console.*`. ## §12 Пути и файловая система

**Устранено в сессии 3, раздел оставлен как диагностика.** Проект переехал на
`/Users/strix/Documents/Projects/warehouse.argomedia.uz` — путь целиком ASCII.
На старом месте лежит симлинк, так что оба адреса рабочие; канонический — новый.

**Что было.** Родительский каталог назывался `Документы\xa0— Alisher’s MacBook Air`,
где `\xa0` — **неразрывный пробел `U+00A0`** (плюс типографский апостроф `U+2019`).
Так macOS называет папку при работе iCloud с «Рабочим столом и Документами»:
«Документы — <имя Mac>». Символ невидим глазом и в выводе `ls` неотличим от обычного
пробела.

**Механизм отказа.** Путь ездит через промпты и сообщения, где `U+00A0`
нормализуется в обычный `U+0020`. Дальше:

- `cd` получает НЕсуществующий путь и падает с «no such file or directory» —
  на каталоге, который открыт в IDE прямо сейчас;
- `Write` по абсолютному пути **не падает**: он молча создаёт недостающие каталоги
  и пишет файл в дерево-двойник. Инструмент рапортует успех, `ls` и `git status`
  файла не видят. Ровно это случилось в с2 — файл потом искали `find`'ом.

**Правила.**
- [ ] Новый проект — сразу под ASCII-путь. Кириллица, апострофы и «умные» тире в
      пути каталога стоят дешевле переезда только до первого агента.
- [ ] `cd` упал на каталоге, который заведомо существует → не искать опечатку,
      а проверить кодовые точки:
      `python3 -c "print(' '.join(f'U+{ord(c):04X}' for c in '<путь>'))"`.
- [ ] Инструмент записи отрапортовал успех → факт проверяется `ls`, а не ответом
      инструмента. Отрицательный результат обязан быть машинным.
- [ ] Заподозрил дерево-двойник → `find ~/Documents -name "<имя файла>"`, перенести
      настоящий файл, пустой дубль снести.

**Чего тут НЕТ и не было: iCloud проекту не мешал.** Заглушек `*.icloud` в дереве
нет, `~/Documents` — обычный локальный каталог, а не симлинк на CloudDocs.
`npm install` в облако не синхронизируется. Не лечи не ту болезнь (с3).
