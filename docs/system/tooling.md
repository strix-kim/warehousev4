## Команды

| Команда | Что делает |
|---|---|
| `npm install` | поставить зависимости (в свежем клоне `node_modules` нет) |
| `npm run dev` | **Vite dev-сервер на закреплённом `http://localhost:5180/`**; требует `.env` |
| `npm run check` | `tsc -b` — быстрая проверка типов без сборки; кэширует, `--force` сбрасывает |
| `npm run build` | `tsc -b && vite build` — основной гейт |
| `npm run build:vercel` | то же с `--mode production` |
| `npm run preview` | локальный просмотр собранного |
| `npm run images:equipment` | пересборка фото оборудования; на macOS требует `sips` и `cwebp` |

**Порт 5180 закреплён `--strictPort` (сессия 3).** Причина: по умолчанию Vite при
занятом порте молча переезжает на соседний, и адрес для приёмки каждый раз новый —
прораб открывает не то. Со `strictPort` занятый порт даёт честную ошибку. На машине
прораба 5173 занят посторонним процессом, поэтому дефолт не годился.

## Чего в проекте НЕТ

Это важнее списка того, что есть: агент не должен ссылаться на несуществующее.

- **Линтера нет.** `.eslintrc.json` в корне — конфиг от прошлого, Vue-стека;
  ни `eslint`, ни `eslint-plugin-vue` не установлены, скрипта `lint` нет.
- **Тестов нет.** `vitest.config.js` — оттуда же (`@vitejs/plugin-vue`, jsdom);
  ни `vitest`, ни `@vue/test-utils` не установлены, скрипта `test` нет.
- **Форматтера как ГЕЙТА нет.** `prettier` не установлен и в скриптах не вызывается.
  Но сам `.prettierrc` — **не призрак**: его настройки (`printWidth: 100`, `semi: false`,
  `singleQuote: true`, `tabWidth: 2`, `trailingComma: es5`) ТОЧНО совпадают с
  фактическим стилем `src/react`. Это действующая конвенция кода — соблюдай её
  руками. Не ставь `.prettierrc` в один ряд с двумя конфигами ниже.
- **CI нет.** Ни `.github/workflows`, ни другого автоматического прогона.

Единственные автоматические гейты — типы и сборка. Всё остальное ловит прораб
глазами и прогон под двумя аккаунтами. Это **записанный долг**
(`docs/project/backlog.md`), а не норма — не выдавай его за достаточную проверку.

## Окружение

**Расположение проекта: `/Users/strix/Documents/Projects/warehouse.argomedia.uz`** —
путь целиком ASCII, и это не косметика. До сессии 3 проект лежал в каталоге, в имени
которого стоял неразрывный пробел `U+00A0` («Документы — Alisher’s MacBook Air»):
путь ломался при каждой передаче через промпт, где `U+00A0` нормализуется в обычный
пробел. Разбор — `gotchas.md` §12. На старом месте оставлен симлинк; **новые проекты
клади под ASCII-путь сразу.**

| Переменная | Назначение |
|---|---|
| `VITE_SUPABASE_URL` | адрес проекта Supabase |
| `VITE_SUPABASE_ANON_KEY` | публикуемый (anon) ключ |

Оба значения — **публичные**, и агент берёт их сам через Supabase MCP
(`get_project_url` + `get_publishable_keys`), а не просит у прораба: правило 3
`CLAUDE.md` прямо разрешает publishable-ключ на клиенте. Просить прораба лезть в
дашборд за тем, что и так уедет в бандл, — лишний ритуал.

`.env` в git не попадает (`.gitignore`). **Всё с префиксом `VITE_` попадает в бандл** —
класть туда что-то секретное нельзя; `service_role` и токены интеграций живут только
в Edge Functions.

На Vercel переменные задаются отдельно, в настройках проекта: правка `.env.example`
на прод не влияет никак.

## Права агента (`.claude/settings.local.json`)

**Файл вне git** — он попадает под глобальный `~/.config/git/ignore` прораба. Значит
настройки не переезжают на другую машину и не видны второму агенту: восстанавливать
их придётся руками по этому разделу.

Раскладка после с3 — **73 правила в `allow`, 18 в `ask`**:

- **Свободно:** все обычные git-операции (`push`, `merge`, `checkout`, `switch`,
  `fetch`, `pull`, `stash`, `revert`, `cherry-pick`, `tag`), команды сборки,
  читающие инструменты Supabase и Vercel, **`execute_sql` и `apply_migration`**.
- **Под подтверждением, и ни одно не про доверие:** восемь необратимых git-команд
  (`reset --hard`, `clean`, `restore`, `checkout -- `, `push --force`, `push -f`,
  `branch -D`, `rm`) — они уничтожают незакоммиченное, чего не вернёт `git revert`,
  а `git clean -fd` сносит в том числе `.env`. И платные/внешние действия: ветки
  Supabase, создание и пауза проектов, Edge Functions, `deploy_to_vercel`, защита
  деплоев — это счёт и инфраструктура вне репозитория.

**Две грабли, обе стоили времени в с3:**

1. **Правка файла во время живой сессии может быть затёрта.** Claude Code держит
   права в памяти с момента старта и при добавлении нового разрешения (когда прораб
   нажимает «разрешить») переписывает файл ЦЕЛИКОМ из своей памяти. Внешняя правка
   при этом исчезает молча. Отсюда: поправил права — **перезапусти чат**, тогда
   harness перечитает файл; и проверь `git status`/`json.load` после, а не поверь
   ответу инструмента.
2. **Часть блокировок правами не снимается.** Их даёт классификатор auto-mode,
   который смотрит на СМЫСЛ команды, а не на список: так был отклонён
   `python3 - <<'PY'`, переписывающий файл. Ни одно правило в `allow` этого не
   изменит, и не надо — правильный ответ был перейти на штатные `Read`/`Edit`.
   Не ищи в этом файле несуществующее правило.

Инструменты, которыми агент смотрит в прод: схема, миграции, RLS, advisors,
SQL-выборки — Supabase; деплои, build- и runtime-логи — Vercel.

**Состояние: подключён с с2** — id проектов в `current-state.md` и `workflow.md`,

мост слеп, сказать прямо и работать по коду. Подключение — действие прораба.

## Глаза агента (Playwright MCP)

Браузер, которым агент сам открывает приложение: кликает сценарий, снимает экран,
печатает страницу в PDF. Заведён в с24 — до него любая проверка «как это выглядит»
упиралась в прораба, а печать по правилу gotchas §14 вообще нельзя судить иначе
как по самому PDF.

**Объявлен файлом `.mcp.json` в корне** (не в `~/.claude.json`): конфигурация
проектная, её видят и Codex, и Cursor, и она едет вместе с репозиторием. Версия
закреплена точно — `@playwright/mcp@0.0.79`, как и рантайм-зависимости.

| Ключ | Зачем |
|---|---|
| `--caps pdf` | включает `browser_pdf_save`; без него печать не проверить |
| `--user-data-dir .playwright-profile` | профиль браузера НА ДИСКЕ: иначе логин пропадает между запусками и агент не уходит дальше формы входа. Прораб входит один раз в открывшемся окне |
| `--output-dir .playwright-out` | куда падают снимки и логи консоли. ВНИМАНИЕ (с24): `browser_pdf_save` с коротким именем файла пишет НЕ сюда, а в текущий каталог — то есть в корень репозитория. Путь для PDF указывать целиком: `.playwright-out/имя.pdf` |

Оба каталога в `.gitignore`. Окно открывается видимым (headless по умолчанию
выключен) — прораб видит, что агент делает.

**Разделение проверок не отменяется.** Playwright закрывает механические прогоны
(тот же лист печати до и после захода в «Залы», ширина 390, консоль без ошибок).
Вкусовая приёмка — «красиво/некрасиво, понятно/непонятно» — по-прежнему за
прорабом: агент не решает, как продукт должен выглядеть.
