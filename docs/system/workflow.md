# Workflow: сессии, хэндофы, чистый контекст

> Протокол упакован в скиллы Claude Code: `/session-start`, `/checkpoint`,
> `/session-close`, `/rls-verify`, `/deploy-verify` (`.claude/skills/`).
> Скилл = исполняемая копия процедуры отсюда; меняешь протокол здесь — патчи
> соответствующий SKILL.md тем же коммитом (и наоборот). Codex и Cursor исполняют
> те же markdown-скиллы по указателю из `AGENTS.md`; этот файл остаётся источником
> правды для всех сред.
>
> **Это общий протокол проектов прораба, не поделка под один репозиторий.**
> Ритуалы, имена скиллов, нумерация шагов и шаблон хэндофа обязаны совпадать между
> проектами — различается только предметный слой. Всё, что зависит от стека,
> собрано в двух секциях: «Гейты стека» и «Мост». Меняешь ритуал — меняешь его
> во всех проектах, иначе система расползётся на три диалекта.

## Зачем это

Длинный чат = замусоренный контекст = падает качество кода и внимания.
Поэтому: работаем короткими сессиями, между ними — передача смены (handoff)
и чистка чата. Контекст живёт в файлах, а не в переписке.

## Правило №1: одна сессия = одна цель

Цель формулируется одним предложением и является проверяемой.
Примеры: «редактор списка сохраняет смешанный состав», «починить дубль позиции
при быстром клике», «подключить экспорт в Excel».
Не цель: «поработать над списками».

## Жизненный цикл сессии

### Старт

1. Корневые инструкции агента подхватываются автоматически:
   `CLAUDE.md` для Claude Code, `AGENTS.md` для Codex и Cursor.
2. Прочитай `docs/project/current-state.md`.
3. Открой handoff, явно названный актуальным в `current-state.md`. Если указателя
   нет — выбери файл с наибольшим номером сессии в имени; обычной лексической
   сортировке не верь (`9` сортируется после `10`).
   `docs/project/backlog.md` отсутствует → создай пустой с заголовком.
   Нет ни `current-state.md`, ни хэндофов вообще → это ПЕРВАЯ сессия проекта:
   предложи прогнать болванку `docs/system/product-doc-guide.md`, код до неё не пишем.
   Handoff выбран → сверь строку «Последний doc-audit» в `current-state.md`:
   отстаёт на ~5+ кодовых сессий → предложи `/doc-audit` вместе с целью сессии.
4. Быстрый `git log -5` + `git status`: свежие коммиты и незакоммиченные хвосты
   (чужие правки в рабочей ветке — сигнал живой параллельной сессии, см. раздел ниже).
   **Отдельно сверь ветку:** `git branch --show-current`. Ты на `main` → см. «Прод и ветки».
5. Проверь мост и рабочее окружение (раздел «Мост»). Мост слеп — назови это прямо
   и не притворяйся, что видишь прод; работай по фактам из кода и по тому, что
   принесёт прораб.
6. «Следующий шаг» из handoff и «Очередь целей (топ-3)» из current-state (№1 —
   кандидат на цель этой сессии). Шаг начинается с ПРОВЕРКИ («убедиться, что
   миграция доехала до прода») → выполни её сейчас и доложи результат прорабу,
   не откладывая на после согласования цели.
7. Сформулируй цель сессии, согласуй с прорабом. Без согласованной цели код не пишем.
   Прораб может перебить цель своей — это нормально, его цель приоритетна.

### Работа

Цикл: шаг → чекпоинт в браузере → подтверждение прораба → следующий шаг.
Принятый чекпоинт оформляется через `/checkpoint` — порядок гейтов строгий
(команды — в секции «Гейты стека»). Чекпоинт всегда конкретный: «открой
`/equipment`, вбей в поиск «Shure», нажми на строку — справа откроется превью,
кнопка «Добавить» останется отдельной».

**Разделение проверок.** Визуальные проверки «открыть и посмотреть» в браузере
делает САМ прораб — агент не гоняет циклы скриншотов ради приёмки. Агент к приёмке
даёт факты в цифрах (SQL-выборка, build-лог, runtime-лог, размер бандла) и короткий
нумерованный чеклист «что нажать → что увидеть → что должно оказаться в базе».
Скриншоты и браузерная автоматизация — точечно, по явной просьбе прораба.

**Прогон под двумя аккаунтами обязателен**, если в цели сессии:
новая или изменённая RLS-политика · новая таблица или колонка, которую читает
клиент · права на чужие записи (удаление, редактирование, видимость) · роли ·
что-то, что «у автора работает». Одна вкладка и один аккаунт маскируют дыры в RLS
ровно так же, как соло-запуск маскирует баги репликации. Процедура и чеклист —
`/rls-verify`. Результат фиксируется в handoff текущей сессии: что гоняли, что
видели, чего НЕ проверили. Прогон сознательно пропущен — это явное решение
прораба: записать его в handoff и строкой в `docs/project/backlog.md`.
Молчаливый пропуск копит системный долг.

**Гейт схемы.** Новая таблица, колонка, политика или индекс сначала описываются
файлом миграции в `supabase/migrations/`, и только потом применяются. Правка
схемы кликами в дашборде без миграции — это потеря источника правды
(см. «Второй источник правды»).

### Финиш

Триггеры закрытия: цель достигнута / контекст раздулся / переключаемся
на другую подсистему / накопилось 2+ незакрытых бага / прораб поправляет
по второму кругу.

По команде прораба «закрываем сессию» (**порядок шагов строгий**: номер → handoff
→ current-state — указатель в сводке должен вести на уже созданный файл):

1. **Номер сессии `N`** = максимальный номер в именах `docs/handoffs/YYYY-MM-DD-N-…`
   плюс один. Номер сквозной и обязан расти: 21, 22… Дата помогает человеку,
   порядок задаёт номер. Старые однозначные номера не переименовываем — на них
   ссылается история. Рядом идёт живая параллельная сессия → номера разбираются
   по правилу «кто закрывается первым, берёт меньший `N`».
2. Создай handoff: `docs/handoffs/YYYY-MM-DD-N-краткая-цель.md` по шаблону ниже.
   Честно фиксируй непроверенное (непринятая миграция, пропущенный прогон под
   двумя аккаунтами) — следующая сессия начнёт с этого.
3. Обнови `docs/project/current-state.md` — это ПЕРЕЗАПИСЫВАЕМАЯ сводка «как есть
   сейчас», не журнал: итог сессии = 2–3 строки в нужных секциях (устаревшие
   утверждения заменяются, посессионные блоки «Сессия N» не заводятся);
   подробности живут только в handoff. Очередь целей топ-3: сделанное
   вычеркнуть, №1 = следующая сессия; перебитая прорабом цель сдвигается вниз,
   не исчезает. Файл перерос **~450 строк** → предложи прорабу ужимку (ниже
   ~400 строк сводка не сжимается без потери фактов). Резать в первую
   очередь: посессионную хронику, протоколы уже закрытых проверок, историю
   переездов, описания удалённых сущностей — подробности этих сессий уже
   лежат в своих хэндофах.
   **Как ужимать:** режь СТРУКТУРУ, а не фразы — слияние родственных буллетов и
   вынос деталей в библию по ссылке дают строки, переформулировка почти ничего
   не даёт. Два обязательных grep-прогона: ДО реза сверить срезаемые абзацы по
   `docs/project/01–06`, `docs/system/`, `.claude/skills/` (факта нет больше
   нигде → не режем, а ужимаем до строки), ПОСЛЕ реза — по числовым инвариантам
   и именам модулей. `git diff` потерю факта не ловит в принципе. **Порог —
   ориентир, а не цель:** критерий остановки — «следующая срезанная строка уносит
   факт, которого нет больше нигде»; недобор до цифры объявляй прорабу числами
   по разделам. Ужимку выгоднее всего гнать СРАЗУ после `/doc-audit`.
   **Обязательный подшаг:** строку «**Актуальный handoff:**» перевести на путь
   файла из шага 2. По этому указателю стартует следующая сессия — забыть его
   значит сломать старт; это самый дорогой промах закрытия.
4. Записать изменения в доки — в ДВУХ местах, если применимо:
   - `docs/project/decisions.md` — строка про новое решение/архитектуру
     (журнал = история «что решили», append-only). Журнал — только-на-запись:
     в обычной работе его НЕ читаем («как есть сейчас» держат 01–06 и
     current-state); открывается точечно (grep по ключу, не целиком) при
     вопросе «почему решили X» или в доко-аудите.
   - Затронутая страница из `docs/project/01–06`, если решение меняет её содержание
     (модель данных, функция, права, числа, роадмап, дизайн-система) — патчим её
     в ТОМ ЖЕ коммите. decisions.md фиксирует «что решили», 01–06 держит
     «как есть сейчас» (перезаписываемая картина). Расходятся — библия гниёт.
   - Побочные идеи/баги, не взятые в работу → строка в `docs/project/backlog.md`.
5. Гейты и финальный commit сессии (если есть незакоммиченное) — команды в
   «Гейты стека». Сообщение коммита — формата `доки: закрыть сессию N — <суть>`.
   Кодовые правки в норме уже закоммичены чекпоинтами; незакоммиченный код в
   хвосте — сигнал спросить прораба, принят ли он.
   **Push — по правилам секции «Прод и ветки», а не автоматом.**
6. Была правка схемы базы или данных мимо репозитория (клики в дашборде,
   ручной SQL) → зафиксируй это миграцией и напиши в handoff, что именно
   применено и подтверждено ли (см. «Второй источник правды»).
7. Скажи прорабу: «можно чистить чат» (/clear). Новая сессия начнётся со старта.

Грабля закрытия: кириллицу в доках не править через perl (`perl -CSD` даёт
мохибейк) — только Edit/Write или python3.

## Шаблон хэндофа

Шаблон общий для всех проектов прораба — менять его в одиночку нельзя.

```md
# Handoff: YYYY-MM-DD (сессия N) — <цель сессии>

## Сделано
- ...

## Проверка
- что и как проверено; чего НЕ проверяли — тоже честно

## Файлы
- изменены: ...
- созданы: ...
- вне git (схема БД, данные, настройки хостинга): ...

## Состояние
- работает: ...
- не работает / известные баги: ...

## Следующий шаг
<одно конкретное первое действие следующей сессии>

## Грабли и решения
| Симптом | Причина | Решение |
|---|---|---|
| ... | ... | ... |
```

## Гейты стека

Единственное место, где протокол зависит от технологии. Другой проект — другая
эта секция, всё остальное в файле совпадает.

**Стек:** React 19 + TypeScript 5.9 + Vite 7, Supabase (Postgres + Auth + Data API),
хостинг Vercel. Node 22.x.

**Порядок гейтов чекпоинта строгий:**

```bash
npx tsc -b                 # типы; падает — чиним до коммита
npm run build              # tsc -b && vite build; падает — чиним до коммита
git diff --check           # висячие пробелы и маркеры конфликтов
```

Правился SQL — миграция обязана лежать файлом в `supabase/migrations/`
(см. «Второй источник правды»).

**Чего в проекте НЕТ и на что нельзя ссылаться:** линтера и тестов. `.eslintrc.json`
и `vitest.config.js` — конфиги-призраки от прошлого стека, ни `eslint`, ни `vitest`
не установлены, скриптов `lint`/`test` в `package.json` нет. Пока их не заведут,
единственные автоматические гейты — типы и сборка; всё остальное ловит прораб
глазами и прогон под двумя аккаунтами. Это записанный долг, а не норма.

**Первый запуск в свежем клоне** (нет `node_modules`, нет `.env`):

```bash
npm install
cp .env.example .env       # значения — из дашборда Supabase, в git не попадают
npm run dev
```

## Мост

Аналог «агент сам видит прод, а не гоняет прораба за скриншотами».

- **Supabase MCP** — схема, миграции, RLS, advisors, логи, SQL-выборки.
- **Vercel MCP** — деплои, build-логи, runtime-логи и ошибки.

**Состояние на сегодня: мост к этому проекту НЕ подключён.** Коннектор Supabase
видит только чужую организацию, коннектор Vercel — только чужие проекты; ни базы
склада, ни его деплоя в них нет. Пока это так — агент обязан говорить «мост слеп»
и работать по коду и по тому, что принесёт прораб. Притворяться, что видишь прод,
запрещено: выдуманный факт о живой базе дороже любого молчания.

Проверка моста в начале сессии — две команды: `list_projects` у Supabase и
`list_projects` у Vercel. Проекта склада нет в ответе → мост слеп, доложить одной
строкой и идти дальше.

Чтобы мост появился: подключить в настройках коннекторов ту организацию Supabase
и тот аккаунт Vercel, где живёт склад. Это действие прораба, не агента.

## Прод и ветки

**`main` — это прод. ФАКТ, проверен в сессии 2:** все 20 последних деплоев Vercel —
`target: production`, `githubCommitRef: main`. Домены — `warehouse.argomedia.uz`,
`warehousev4.vercel.app` и branch-алиас `main`. Push ветки Vercel собирает как превью,
прод не трогает — проверено с обеих сторон. Репозиторий — `github.com/strix-kim/warehousev4`.

**Осторожный режим сессий 1–2 СНЯТ решением прораба (сессия 3).** Основание
продуктовое, не техническое: это внутренняя система для нескольких сотрудников
ARGO Media, а не публичный сервис. Внешних пользователей нет, аптайм ничего не
приносит и не теряет, откат стоит `git revert` плюс минуты пересборки. Ритуал,
тормозящий каждую сессию ради риска такого размера, — плохой обмен.

- Работа идёт в ветке: `git checkout -b session-N-тема`. Ветка остаётся единицей работы:
  это дёшево и даёт превью-деплой для приёмки.
- **Слияние в `main` отдельной команды больше НЕ требует.** Мера осталась одна, и она
  про содержимое, а не про разрешение: **сливаем принятое** — чекпоинт, подтверждённый
  прорабом, с зелёными `npm run check` и `npm run build`. Непринятое и несобирающееся
  в `main` не едет: не из страха прода, а потому что поверх непринятого не строят.
- Прораб сказал «выкатывай» / «мержим» — сливаем сразу, без переспрашивания.
- Агент оказался на `main` с незакоммиченными правками → всё равно увести в ветку:
  ветка нужна для превью-деплоя и чистой истории, а не как защита от прода.
- **Что осталось строгим:** запись в прод-БАЗУ (данные, схема, политики) — по-прежнему
  только с явного разрешения прораба, на каждое действие отдельно. Код откатывается
  ревертом, удалённые строки — нет. Это правило 8 `CLAUDE.md`, оно не смягчалось.
- Смягчение зафиксировано в `decisions.md` (сессия 3). Ужесточать обратно — тоже явным
  решением прораба и правкой этой секции.

## Второй источник правды: схема базы

Код живёт в git. **Схема и данные Supabase живут ВНЕ git** — как и в других
проектах прораба, где рядом с репозиторием есть второй источник правды, который
git не видит. Отсюда правила:

1. Любое изменение схемы — файлом в `supabase/migrations/` с осмысленным именем.
   Применено кликами в дашборде — всё равно фиксируется миграцией задним числом,
   в ту же сессию.
2. `scripts/*.sql` — исторические ручные скрипты. Гарантии, что они применены,
   нет; новые SQL туда не кладём.
3. **Запись в прод-базу — только с явного разрешения прораба.** Чтение (выборки,
   advisors, логи) свободно, когда мост подключён. Массовые UPDATE/DELETE и
   изменения политик — отдельное подтверждение на каждое действие.
4. В `.env` лежат ключи. В git они не попадают и в чат не пересказываются.

## Сигналы по ходу сессии (отслеживаешь ты, ИИ)

Не жди команды — заметил сигнал, предложи действие сам:

- Прораб поправляет тебя по второму кругу, или ты перечитываешь файлы,
  которые уже читал в этой сессии → контекст замусорен: предложи закрыть
  сессию по протоколу и продолжить в свежей.
- Всплыл нетривиальный баг посреди другой цели → предложи зафиксировать его
  в handoff и разобрать отдельной сессией: свежий контекст дебажит лучше.
- С последнего доко-аудита накопилось ~5+ кодовых сессий или впереди крупная
  веха → предложи `/doc-audit` (сверка библии 01–06 с кодом): дрейф,
  пойманный рано, — 10 минут приёмки; поздно — reconcile-сессия.
- Правка касается прав, ролей или чужих записей → напомни про `/rls-verify`
  до закрытия цели.
- Handoff-файлы никогда не удаляем: это история проекта и сырьё для будущих
  скиллов.

## Параллельные сессии двух агентов

Одна рабочая копия, два агента одновременно — риск: незакоммиченные чужие правки
смешиваются с твоими, а оборванная соседняя сессия оставляет висяк без хэндоффа.

Правила:

1. **Каждая сессия работает в своей git-ветке** (`session-N-тема`); `main` держит
   только выкаченное.
2. Закрытие ветки = приёмка прораба + слияние тем же закрытием сессии; handoff
   пишется как всегда.
3. Коммитим только СВОИ файлы поимённо, никаких `git add -A` — защита на случай,
   если правило ветки нарушено и в копии всё же двое.
4. Номера хэндоффов: кто закрывается первым, берёт меньший `N`.
5. На старте сессии видишь чужие незакоммиченные правки → не трогай их
   и не коммить; спроси прораба, жива ли соседняя сессия.

## Аварийное восстановление

Сессия оборвалась без хэндоффа (чат потерян, машина упала):

1. Новая сессия начинает с `git log -5`, `git status`, `git branch --show-current`
   и `current-state.md`.
2. Восстанови картину: что закоммичено, что висит незафиксированным, в какой ветке.
3. Создай короткий хэндофф задним числом (что удалось установить).
4. Согласуй с прорабом цель заново — не продолжай старую вслепую.
