# Workflow: сессии, хэндофы, чистый контекст

> Процедуры живут в скиллах `.claude/skills/` — `/session-start`, `/checkpoint`,
> `/session-close`, `/rls-verify`, `/deploy-verify`, `/doc-audit`. Этот файл —
> **правила**, которые скиллы исполняют: зачем сессии, ветки и прод, гейты стека,
> мост, второй источник правды, сигналы. Codex и Cursor читают те же скиллы по
> указателю из `AGENTS.md`.
>
> **С с9 протокол этого проекта сокращён решением прораба** и с другими его проектами
> больше не обязан совпадать: доку читает только агент, поэтому снято всё, что
> дублирует git или ловится первым же рабочим вызовом (проверка моста и окружения
> на старте, журнал `decisions.md`, списки файлов в хэндоффе, якоря `файл:строка`
> в библии, ужимка current-state по порогу). Что именно и почему — handoff с9.

## Зачем это

Длинный чат = замусоренный контекст = падает качество кода и внимания.
Поэтому: работаем короткими сессиями, между ними — передача смены (handoff)
и чистка чата. Контекст живёт в файлах, а не в переписке.

## Правило №1: одна сессия = одна цель

Цель формулируется одним предложением и является проверяемой.
Примеры: «редактор списка сохраняет смешанный состав», «починить дубль позиции
при быстром клике», «подключить экспорт в Excel».
Не цель: «поработать над списками».

## Жизненный цикл сессии

**Старт** — `/session-start`: current-state → актуальный handoff → git → ветка →
цель. Без согласованной цели код не пишем; цель прораба приоритетна.

**Работа** — цикл: шаг → чекпоинт в браузере → подтверждение прораба →
`/checkpoint` (гейты строгим порядком, коммит, слияние принятого). Чекпоинт всегда
конкретный: «открой `/equipment`, вбей «Shure», нажми на строку — справа откроется
превью».

- **Разделение проверок.** Визуальные проверки в браузере делает САМ прораб —
  агент не гоняет циклы скриншотов ради приёмки. Агент к приёмке даёт факты в
  цифрах (SQL-выборка, build-лог, runtime-лог, размер бандла) и нумерованный
  чеклист «что нажать → что увидеть → что должно оказаться в базе». Скриншоты и
  браузерная автоматизация — точечно, по явной просьбе.
- **Прогон под двумя аккаунтами обязателен**, если в цели: новая или изменённая
  RLS-политика · новая таблица или колонка, которую читает клиент · права на
  чужие записи · роли · что-то, что «у автора работает». Процедура — `/rls-verify`;
  результат — в handoff. Сознательный пропуск — решение прораба, записать в handoff
  и строкой в `backlog.md`; молчаливый пропуск копит системный долг.
- **Гейт схемы.** Таблица, колонка, политика, индекс сначала описываются файлом в
  `supabase/migrations/`, потом применяются (см. «Второй источник правды»).

**Финиш** — `/session-close`: номер → handoff → current-state с указателем →
библия тем же коммитом → гейты по необходимости → коммит, push, слияние принятого.
Триггеры: цель достигнута / контекст раздулся / смена подсистемы / 2+ незакрытых
бага / прораб поправляет по второму кругу.

**Принцип документации:** handoff хранит только то, чего нет в git (непроверенное,
вне git, следующий шаг, грабли, «почему»); current-state — сводка «как есть
сейчас», не журнал; библия 01–06 — «как устроено», ссылки на код именем файла и
функции; `backlog.md` — парковка. `decisions.md` заморожен с с9.

## Гейты стека

Единственное место, где протокол зависит от технологии.

**Стек:** React 19 + TypeScript 5.9 + Vite 7, Supabase (Postgres + Auth + Data API),
хостинг Vercel. Node 22.x.

**Порядок гейтов чекпоинта строгий:**

```bash
npx tsc -b                 # типы; падает — чиним до коммита
npm run build              # tsc -b && vite build; падает — чиним до коммита
git diff --check           # висячие пробелы и маркеры конфликтов
```

Правился SQL — миграция обязана лежать файлом в `supabase/migrations/`.

**Чего в проекте НЕТ и на что нельзя ссылаться:** линтера и тестов. `.eslintrc.json`
и `vitest.config.js` — конфиги-призраки от прошлого стека, ни `eslint`, ни `vitest`
не установлены, скриптов `lint`/`test` в `package.json` нет. Единственные
автоматические гейты — типы и сборка; остальное ловит прораб глазами и прогон под
двумя аккаунтами. Это записанный долг, а не норма.

**Первый запуск в свежем клоне** (нет `node_modules`, нет `.env`):

```bash
npm install
cp .env.example .env       # значения — из дашборда Supabase, в git не попадают
npm run dev                # http://localhost:5180/
```

## Мост

Агент сам видит прод, а не гоняет прораба за скриншотами.

- **Supabase MCP** — схема, миграции, RLS, advisors, логи, SQL-выборки.
- **Vercel MCP** — деплои, build-логи, runtime-логи и ошибки.

**Подключён с с2.** Supabase `warehousev4` (`umbqiktyqlfqqgupxqdm`), Vercel
`warehousev4` (`prj_2Xh9KlIRla8fZaF4n8ZcSWDQ14MY`, команда
`team_VVVqjT57YkCiqVBzOXs0OBfs`). На старте сессии мост не проверяем (с9): если
рабочий вызов вернул «проекта нет» — мост слеп, агент говорит это одной строкой и
работает по коду и по тому, что принесёт прораб. Притворяться, что видишь прод,
запрещено: выдуманный факт о живой базе дороже любого молчания. Поднять мост может
только прораб — подключить нужную организацию Supabase и аккаунт Vercel в
настройках коннекторов.

## Прод и ветки

**`main` — это прод. ФАКТ, проверен в сессии 2:** все деплои Vercel —
`target: production`, `githubCommitRef: main`. Домены — `warehouse.argomedia.uz`,
`warehousev4.vercel.app` и branch-алиас `main`. Push ветки Vercel собирает как превью,
прод не трогает. Репозиторий — `github.com/strix-kim/warehousev4`.

**Осторожный режим сессий 1–2 СНЯТ решением прораба (сессия 3).** Основание
продуктовое: внутренняя система для нескольких сотрудников ARGO Media, внешних
пользователей нет, откат стоит `git revert` плюс минуты пересборки.

- Работа идёт в ветке `session-N-тема`: дёшево и даёт превью-деплой для приёмки.
- **Слияние в `main` отдельной команды не требует.** Мера одна, про содержимое:
  **сливаем принятое** — чекпоинт, подтверждённый прорабом, с зелёными гейтами.
  Непринятое и несобирающееся в `main` не едет: поверх непринятого не строят.
- Прораб сказал «выкатывай» / «мержим» — сливаем сразу, без переспрашивания.
- Агент оказался на `main` с незакоммиченными правками → увести в ветку.
- **Запись в прод-базу открыта** (с3): `execute_sql` и `apply_migration` в `allow`.
- **Вместо барьера — обязанность предупреждать.** `DELETE`/`UPDATE`/`DROP`/`TRUNCATE`
  по живым данным и смена политик кладутся прорабу текстом с оценкой «сколько строк
  заденет» и исполняются тем же ходом (с8: без паузы «выполню, если не остановишь»).
  Это не запрос разрешения — гарантия, что необратимое не случится втихую.
  `SELECT` и миграции, добавляющие объекты, — свободно.
- **Под подтверждением остались только платные и внешние действия:** ветки Supabase
  (`create_branch`, `merge_branch`, `reset_branch`, `delete_branch`), создание и
  пауза проектов, Edge Functions, `deploy_to_vercel`, защита деплоев.
- Разрешения инструментов — allowlist в `.claude/settings.json` проекта (с8);
  повторяющуюся команду добавлять туда, а не спрашивать каждый раз.

## Второй источник правды: схема базы

Код живёт в git. **Схема и данные Supabase живут ВНЕ git.** Отсюда:

1. Любое изменение схемы — файлом в `supabase/migrations/` с осмысленным именем.
   Применено кликами в дашборде — фиксируется миграцией задним числом в ту же сессию.
2. `scripts/*.sql` — исторические ручные скрипты. Гарантии, что они применены,
   нет; новые SQL туда не кладём.
3. В `.env` лежат ключи. В git они не попадают и в чат не пересказываются.

## Сигналы по ходу сессии (отслеживаешь ты, ИИ)

- Прораб поправляет по второму кругу, или ты перечитываешь уже прочитанные файлы →
  контекст замусорен: предложи закрыть сессию и продолжить в свежей.
- Нетривиальный баг посреди другой цели → зафиксировать в handoff и разобрать
  отдельной сессией: свежий контекст дебажит лучше.
- Впереди крупная веха или переписана подсистема → предложи `/doc-audit`.
- Правка касается прав, ролей или чужих записей → `/rls-verify` до закрытия цели.
- Handoff-файлы никогда не удаляем: это история проекта.

## Параллельные сессии двух агентов

Одна рабочая копия, два агента одновременно — риск смешать незакоммиченные правки.

1. Каждая сессия работает в своей ветке `session-N-тема`; `main` держит только
   выкаченное.
2. Закрытие ветки = приёмка прораба + слияние тем же закрытием; handoff как всегда.
3. Коммитим только СВОИ файлы поимённо, никаких `git add -A`.
4. Номера хэндоффов: кто закрывается первым, берёт меньший `N`.
5. На старте видишь чужие незакоммиченные правки → не трогай и не коммить; спроси
   прораба, жива ли соседняя сессия.

## Аварийное восстановление

Сессия оборвалась без хэндоффа: `git log -5`, `git status`, `git branch
--show-current`, current-state → картина «что закоммичено, что висит, в какой
ветке» → короткий handoff задним числом → цель согласовать заново, старую
вслепую не продолжать. Подробно — `/session-start`.
