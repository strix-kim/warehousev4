# Проверка доставки правки

Аналог «увидеть результат в живой игре» в других проектах прораба. Здесь живая
среда — превью-деплой ветки и прод, а не локальный dev-сервер: `npm run dev`
доказывает только то, что код собирается у тебя.

## Уровни проверки — от дешёвого к дорогому

1. **Типы и сборка (всегда, бесплатно):**
   ```bash
   npm run check
   npm run build
   ```
   Заодно посмотри размер бандла в выводе Vite — рост чанка больше 500 КБ Vite
   назовёт сам; молчаливый рост тоже стоит заметить и записать.

2. **Локальный прогон** — только чтобы самому убедиться, что не сломал очевидное:
   ```bash
   npm run dev
   ```
   Требует заполненного `.env`. Визуальную приёмку по правилу разделения проверок
   делает прораб, не агент.

3. **Превью-деплой.** Push ветки → Vercel собирает превью. Прод не трогается.
   Это и есть безопасная «живая» проверка.

4. **Прод** — слияние в `main`. Отдельной команды не требует (осторожный режим снят
   в с3), но требует принятой прорабом работы и зелёных гейтов. После слияния
   ОБЯЗАТЕЛЬНО дождись `READY` у прод-деплоя и проверь домен — выкатка без проверки
   результата не считается сделанной.

## Что снимает агент (когда мост подключён)

- Vercel: `list_deployments` → взять последний по ветке; `get_deployment` —
  статус и URL; `get_deployment_build_logs` — почему упала сборка;
  `get_runtime_logs` и `get_runtime_errors` — что валится у живых пользователей.
- Supabase: точечная выборка, подтверждающая, что правка действительно записала
  в базу то, что обещала; `get_advisors` — не появилось ли новых предупреждений
  безопасности или производительности после миграции.

**Мост подключён с с2** (Supabase `warehousev4`, Vercel `warehousev4` — id в
`current-state.md`): уровни 3 и 4 агент снимает сам — `list_deployments` по проекту,
`get_deployment_build_logs`, `get_runtime_errors`, а домен сверяет `curl`'ом по хэшам
чанков в `index.html` против локальной сборки (хэши детерминированы). Превью
снаружи закрыты Vercel Authentication (с6) — их проверяют по логам, кликает прораб.
Вызов моста вернул «проекта нет» (на старте мост не проверяем — с9) → мост слеп,
уровни 3 и 4 подтверждает прораб по чеклисту «открой → нажми → должен увидеть».
Выдумывать состояние деплоя или базы запрещено.

## Чеклист прорабу (шаблон)

```
1. Открой <превью-URL>/<маршрут>
2. Нажми <кнопка>
3. Должен увидеть: <наблюдаемый факт>
4. В базе должно появиться: <таблица, строка, поле = значение>
5. Если не так — принеси текст ошибки из консоли (F12 → Console) и вкладку Network
```

## Перед предложением выкатки

- [ ] `npm run check` и `npm run build` зелёные.
- [ ] Превью-деплой собрался, прораб посмотрел и **принял**. Это единственное
      оставшееся условие выкатки — отдельного «выкатываем» ждать не нужно.
- [ ] Затронуты права/роли/чужие записи → `/rls-verify` пройден.
- [ ] Миграции лежат файлами и применены в том же порядке, в каком поедут в прод.
- [ ] После слияния: прод-деплой в состоянии `READY`, домен отвечает, номер деплоя
      записан в handoff.

## Грабли

- Зелёная локальная сборка не означает зелёный деплой: у Vercel своя версия Node
  (`engines.node` = 22.x) и свои переменные окружения.
- Переменные окружения задаются в Vercel отдельно от `.env` — правка `.env.example`
  на прод не влияет никак.
- `vercel.json` кэширует `/assets/`, `/equipment-images/` на год как immutable:
  «не обновилось» после выкатки — сначала проверь, не смотришь ли ты в кэш.
- Рерайт `/(.*) → /` означает SPA-роутинг: любой несуществующий путь вернёт
  приложение, а не 404 сервера. «Страница открылась» ≠ «маршрут существует».
- Правка схемы едет в прод НЕ через git: миграцию надо применить отдельно.
  Код, ожидающий новой колонки, выкаченный раньше миграции, кладёт приложение.
