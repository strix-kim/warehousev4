# Доко-аудит: библия 01–06 против кода

Зачем: правило «решение трогает 01–06 → патчи страницу тем же коммитом»
(workflow.md, «Финиш») соблюдается не всегда. Регулярный дешёвый аудит ловит
дрейф раньше, чем он потребует переписки. У этого проекта есть свой прецедент:
на момент заведения харнесса правила Cursor описывали Vue-стек, которого в проекте
нет, а `docs/ARCHITECTURE.md` — структуру, которой нет. Доки, которые врут, хуже
отсутствующих: агент им верит.

## Триггеры

- С последнего аудита прошло ~5+ КОДОВЫХ сессий (аудиты видны в хэндоффах:
  ищи «доко-аудит»/«сверка доков»).
- Впереди крупная веха.
- Команда прораба.

## Шаги

1. **Точка отсчёта.** Найди последний аудит в `docs/handoffs/`. Скоуп = кодовые
   сессии после него (по current-state и хэндоффам).

2. **Сверка по страницам.** Для каждой затронутой страницы `docs/project/01–06`
   сравни утверждения с фактическим кодом (`src/react/`), миграциями
   (`supabase/migrations/`) и current-state:
   - `01-product` — что за продукт, кто пользователь, границы («что НЕ входит»);
   - `02-features` — функции по шаблону: что делает пользователь / что решает
     БАЗА / что показывает КЛИЕНТ / какие таблицы; отказные ветки;
   - `03-data-model` — таблицы, колонки, связи, RLS-политики, индексы; сверять
     с миграциями, а при живом мосте — с реальной схемой;
   - `04-architecture` — структура `src/react`, маршруты, слой данных, кэш и его
     TTL, локализация, сборка и деплой;
   - `05-roadmap` — статусы вех против реально закрытого;
   - `06-design-system` — токены, палитра, типографика, брейкпоинты против
     `styles.css`.
   Страниц много → распараллель субагентами по страницам; каждому — страница +
   указание проверять по коду, не по памяти. Тиры — по политике CLAUDE.md
   «Тиры моделей (Claude 5)»: страничные сверки — Opus (effort high), чисто
   механические grep-прогоны — Sonnet/`scout`.

3. **Механическая проверка призрачных якорей** (дешёвая, ловит целый класс молча).
   Все ссылки вида `файл.ts:N` в `docs/project/` и `docs/system/` сверить с реальной
   длиной файла: файла нет или в нём меньше `N` строк → якорь призрачный.
   Смысловой дрейф видно глазами при чтении; адресный — не видно вовсе, пока не
   пойдёшь по ссылке. Распил модуля или вставка кода в начало файла рвут якоря
   молча.
   **Две ловушки резолвера, обе дают ложную тревогу:** длинные SQL-файлы в тексте
   сокращаются многоточием (легенда — в начале `02-features` и `03-data-model`),
   а голый `api.ts` неоднозначен — их в проекте два, `equipment/` и `lists/`,
   и различаются они только по контексту абзаца. Проверялка, не знающая обеих
   таблиц, объявит призраками сотни живых ссылок.

4. **Отчёт, НЕ правки.** Собери таблицу:
   `страница | что написано | как на самом деле (файл:строка) | предложение`.
   Молча не патчим: расхождение может быть намеренным (история, «как будет»).
   Два агента дали противоположные отчёты — разбери сам ДО того, как нести
   прорабу: часто оба правы и смотрят в разные места, а неверна дока.

5. **Приёмка.** Прораб отмечает, что чинить. Принятое — патчим страницы, строка
   в `decisions.md` («аудит N: сведено X расхождений»), обновление строки
   «**Последний doc-audit: сессия N**» в `current-state.md`, один коммит
   `доки: аудит библии — сессия N`.

6. **Уборка backlog.** Пункты `docs/project/backlog.md`, помеченные закрытыми
   (~~зачёркнуто~~ / «ЗАКРЫТО» / `[x]`), перенеси в секцию «Архив (закрыто)»
   в конце файла — живая часть сверху остаётся короткой. Пункты не удаляем и
   не переписываем — только переносим; у пункта есть живой хвост → хвост
   остаётся сверху отдельной строкой. Пункт выглядит сделанным, но закрытым
   не помечен → это расхождение в отчёт шага 4, не самовольная уборка.

## Грабли

- Не переписывай страницу целиком «раз уж открыл» — только принятые расхождения;
  переписка целиком = потерянные нюансы.
- Блоки, явно помеченные историей («старая версия», «до переписывания на React»), —
  не расхождения.
- Атрибуцию сессии сверяй по `git log -S`, а не по комментарию в коде: комментарий
  «правка аудита с N» означает НАХОДКУ аудита N, а не сессию реализации.
- Кириллицу не править через perl — только Edit/Write или python3.
- `AGENTS.md` ↔ `CLAUDE.md` тоже дрейфуют — при аудите сверь и их парность.
- `workflow.md` ⇄ протокольные скиллы (`session-start`/`checkpoint`/`session-close`/
  `rls-verify`/`deploy-verify`) обязаны совпадать по шагам и шаблону хэндофа.
- **Межпроектная сверка.** Ритуалы и шаблон хэндофа общие для всех проектов
  прораба. Раз в несколько аудитов сравни `workflow.md` и одноимённые скиллы
  с соседним проектом: разойтись должны только секции «Гейты стека» и «Мост».
  Разошлось что-то ещё — это дрейф, а не адаптация.
