## Незыблемо (архитектура)
- **База авторитетна:** права, видимость, целостность и уникальность живут в
  Postgres (RLS, CHECK, UNIQUE, FK, триггеры). Правило, существующее только в
  React, не существует.
- **Клиенту не верим:** клиентская проверка — это UX, а не защита. Каждой такой
  проверке нужна пара в базе.
- **Ничего секретного на клиенте:** всё с префиксом `VITE_` попадает в бандл.
- **Схема — только миграциями** в `supabase/migrations/`; схема живёт вне git.
- **Один источник правды** на сущность, особенно между базой и `persistentCache`.
- **Мёртвая зона:** всё в `src/`, что не `src/react/`, — легаси-Vue. Не читать,
  не править, не брать оттуда образцы.
- **Не выдумывай API** — не уверен в методе Supabase/React/React Router, сверься
  с официальной документацией.

## Формат плана
- **Маленькие шаги:** каждый заканчивается конкретным чекпоинтом в браузере
  («открой X, нажми Y → увидишь Z, в таблице T появится строка»).
  Первый шаг по возможности — чистый рефактор / низкорисковый.
- Точные файлы и функции для правок; переиспользуемые существующие утилиты — с путями.
- Изменения схемы — отдельным шагом и отдельной миграцией, ДО кода, который на них
  опирается (иначе выкатка кода раньше миграции кладёт приложение).
- Раздел **рисков**: миграции и обратная совместимость, RLS, кэш и его инвалидация,
  лимит Data API в 1000 строк, размер бандла, то, чего в проекте нет (линтер, тесты).
- Затронуты права/роли/чужие записи → отметь обязательный прогон `/rls-verify`
  под двумя аккаунтами: один аккаунт маскирует дыры в правах.
- Порядок шагов по зависимостям.
